# IssueKit 开发者工具包架构

状态：首批实现，2026-10-23。以下基线审视基于 0.1.6；首批改动与未完成能力见文末实施记录，目标设计不等于全部已实现。

## 产品定位

IssueKit 是面向开发者的工程工具包，在开发周期的关键节点，帮助 Agent 理解约束、做出工程判断、完成工作并交付可验证的结果。

架构师视角体现在判断质量：识别真正的问题、业务与技术边界、变更影响、可复用能力、兼容与演进成本、验证缺口和恢复条件。帮助应与任务规模相称；一个小修复可以直接完成，一个跨服务变更可能需要设计与迁移决策，不以文档数量衡量价值。

开发者可以从任一节点进入，调用单个工具或组合多个工具。Skill 不替代用户决策，不自动扩大提交、发布和外部写入授权。工具包不承担模型调度、通用 Agent 执行引擎或生产发布平台的职责。

## 0.1.6 基线架构与缺口

- `src/issuekit/bundled_skills/` 是发行内容源，含 10 个 Skill 及配套资源；项目安装目录是副本，不是另一份发行源。
- `agent_skills.py` 安装入口、按需资源和 Codex 元数据；Agent 注册表处理四种宿主的安装路径差异。
- `init/upgrade` 分发 Skill、模板和项目配置；当前 upgrade 覆盖同名资源，没有已安装版本与内容摘要，也没有本地修改冲突保护。
- 现有测试覆盖资源复制、元数据选择和项目自有文件保留，不覆盖 Agent 触发准确性或工程任务结果。
- 旧 Skill 多以顺序流程与文件模板组织，merge 以原则和门禁组织，整体协作契约尚不一致。

## 统一的工具契约

每个 Skill 都应清楚表达下列内容，但无需复制同一组标题或强制输出统一表格：

| 契约 | 要回答的问题 |
| --- | --- |
| 决策职责 | 当前帮助开发者解决什么问题，做到哪里结束？ |
| 输入与事实 | 需要哪些意图、约束、代码和证据？材料不完整时如何自主补足？ |
| 判断原则 | 哪些业务意图、边界和工程属性必须守住？哪些取舍可以自主完成？ |
| 交付结果 | 什么实际成果能推进当前工作，如何让人理解并核验？ |
| 完成门禁 | 什么证据足以支持结论，哪些未知不能假装通过？ |
| 授权与兜底 | 哪些动作在本次授权内，哪些歧义或风险需要人工介入？ |

这里规定判断责任和结果边界。只有确定性工具的调用协议或确有脆弱性的操作才需要具体步骤，不为开放式分析和实现规定统一命令顺序。

共同原则：保全仍有效的业务意图；以真实代码与环境事实核对资料；明确区分事实、假设和决策；优先复用；修复完整但不扩张无关范围；验证结论绑定版本；尽力完成后再以具体决策点请求人工兜底。

## 各节点的职责边界

以下为目标职责，不要求按表格顺序执行。

| Skill | 核心问题 | 主要输入 | 应交付的结果 | 边界 |
| --- | --- | --- | --- | --- |
| knowledge | 当前系统如何工作，哪些约束与本次任务有关？ | 代码、项目约定、有效文档 | 带证据和适用范围的上下文 | 不为小任务强制先建设全库 |
| require | 应实现什么行为，如何判断成功？ | 用户目标、当前行为、业务约束 | 需求范围、验收标准、关键歧义 | 不默认建分支，不代替技术选型 |
| design | 如何以合理成本完成目标并支持演进？ | 已明确的需求意图、真实实现、工程约束 | 方案取舍、边界、契约、迁移和验证考虑 | 材料不限于某个文件，不把固定步骤当设计价值 |
| coding | 如何完成最小完整实现且不破坏有效能力？ | 明确目标、现有代码、有效设计决策 | 代码、关联更新和验证证据 | 不对关键业务歧义擅自取默认值；外部写入另守授权 |
| test | 风险在哪里，应验证什么、在哪层验证？ | 需求契约、实现变化、已有覆盖 | 验证策略、覆盖关系、关键测试预期 | 不重复维护 business-test 的详细 Case 和运行结果 |
| business-test | 如何将真实业务验证落地并证明结果？ | 验收标准、Case、环境和能力事实 | 可执行 Case、准备状态、运行证据及判定 | 规范定义与执行记录分离；不把 Mock 当真实验收 |
| review | 哪些问题会妨碍正确交付或长期维护？ | 明确的变更范围及相关上下文 | 有证据、严重级别和可行动建议的发现 | 无 PR 也可审核；不默认编辑，不强推单一架构风格 |
| merge | 如何组合改动并保全各方有效能力？ | 选定版本、背景、原有能力和依赖 | 完整集成结果、能力去向与验证证据 | 不以无冲突、代码存在或编译成功替代功能保全 |
| cleanup | 哪些分支和 worktree 已失去独立用途，如何回收并可追查？ | 已核实主分支与任务目标、交付及工作区证据、清理授权 | 执行前清单与理由、逐项结果、持久历史及恢复条件 | 默认仅本地；远端可恢复不等于已交付；归档不等于释放磁盘 |
| release | 当前版本是否具备交付条件？ | 版本、变更、验证、依赖与恢复条件 | 发布准备结论、交付说明及被授权的交付动作 | 准备、提交、推送、创建 PR、部署分别判断范围，不自动串联 |
| change | 目标或决策变化影响什么？ | 新旧意图、决策、代码和证据 | 影响分析、有效材料更新、需重验的范围 | 不止同步文档；不擅自执行受影响的全部实现或线上变更 |

故障诊断和维护演进尚无独立 Skill。现阶段标为能力缺口，积累重复需求及评测证据后再决定新增、扩展或组合已有工具，不预先创建空壳。

## 上下文衔接

衔接围绕意图与证据，而不是文件是否齐全：

- 用户已确认的需求、任务说明、Issue 文档和讨论都可承载目标；代码用于确认事实，不能自行改写明确需求。
- 设计决策记录选择、依据、适用范围和影响，不要求每次输出完整技术方案。
- 交付证据至少能说明受检对象、版本、检查内容、结果和限制；真实执行时另绑定实际环境。没有证据的完成状态不能沿用。
- 决策改变后，只重新评估受影响的实现与验证，不自动重跑全部开发周期。
- 资料不足时先调查。能独立推进的部分继续；只有关键歧义影响正确性且证据不足以裁决时，才向人工提出聚焦问题。

现有 `.issuekit/config.yaml`、`knowledge/`、Issue 目录和模板继续复用。模板是表达工具，不是调用门票。暂不新增通用状态数据库、流程 DSL 或要求所有 Skill 填写的大型 JSON 协议。

## 技术职责分层

| 层 | 负责 | 不承担 |
| --- | --- | --- |
| Skill 内容 | 选择条件、工程原则、必要门禁、按需资源导航 | 模型内部解题步骤、隐含外部授权 |
| 确定性工具 | 可重复的结构、资源、版本、输入输出校验 | 凭格式合格断言业务正确 |
| 项目上下文 | 真实业务规则、领域知识、项目约定、环境与执行记录 | 通用发行内容中的项目特例 |
| 宿主适配 | 安装路径、元数据、宿主支持的调用方式 | 复制维护另一套核心工程规则 |
| 分发与升级 | 打包、来源与版本追踪、资源完整性、修改保护 | 擅自覆盖用户本地定制 |
| 效果评测 | 判断工具是否改善选择与任务结果 | 以关键词匹配或宣传指标代替实际效果 |

入口保留共用决策与门禁，模式细节按需加载；脚本和资源有实际作用才增加。已有 business-test 入口约 3 万字节，优先检查模式重复并合理拆分，不以行数或某个宿主的阈值作为全平台硬标准。

只有出现经验证的跨 Skill 重复规则，才提取共享契约；不先建设复杂继承体系。必要门禁在独立调用时仍应可发现，不能假设某个启动 hook 已经加载。

## 安装升级的目标行为

仍保留当前 Python CLI 与目录结构。最小增量是记录发行版本及受管理文件安装时的内容摘要，而不是更换包管理器。

- 未被本地修改的受管理文件可更新。
- 本地修改与新版内容相同则收敛；存在不同修改时保留并报告冲突，不静默覆盖。
- 无旧安装基线时不能假定本地文件未修改，需提供明确处理选项。
- 新版移除的资源只有在确认归属且未修改时才可按明确升级策略清理；不误删项目自有文件。
- 部分写入失败须报告实际状态并可恢复，不制造“全部升级完成”的错误结论。

Skill 的版本与摘要基线、本地冲突保护及失败重试已在首批实现；文档模板暂时沿用同名覆盖策略，升级前需备份定制模板，不能把 Skill 保护泛称为所有项目文件均受保护。

## 现有内容的重点修订

| 当前问题 | 依据 | 目标调整 |
| --- | --- | --- |
| 依赖指定文档才能设计或编码 | design 的前置条件；coding 的前置条件 | 门禁改为需求与约束是否足够明确，保留必要的人工确认 |
| 需求分析附带切主分支和建分支 | require 的创建 Git 分支章节 | 业务分析与仓库状态变更解耦，遵循实际基线与授权 |
| 实现方式与关键业务决策混在一起 | coding 的固定编码顺序及模糊需求处理 | 允许自主实施；影响外部契约的歧义不能靠“合理默认值”消解 |
| 测试策略与详细 Case 定义有交叠 | test 的黑盒/接口用例与 business-test 的 Case 协议 | test 负责验证策略与覆盖；详细 Case 在一个位置维护，策略引用它 |
| 测试计划可能被当成已执行证据 | release 从 test-plan 获取覆盖和结果 | 计划只证明准备验证什么，运行报告才承载实际结果；以稳定 Case 标识关联 |
| 发布准备绑定推送及创建 PR | release 的创建 Pull Request 章节 | 结果与动作分离，按请求完成已授权工作 |
| 关键基线和架构选择被硬编码 | require/release/review 中的 master；review 中部分固定层次要求 | 依据项目真实基线和约定，评价职责与质量而非强推模式 |
| change 的影响分析偏重文档 | change 的影响分析与更新章节 | 同时报告代码、测试、兼容、数据与交付证据的失效范围 |

以上是 0.1.6 内容审视结果，首批修订状态见文末。契约更新与实现兑现应分别报告，新预期不得覆盖历史执行记录。知识发现与相似门禁的重复可在修订中精简，不因此立即引入新的总控 Skill。

## 最小评测设计

评测内容属于开发仓库，不进入默认分发的 Skill 上下文。真实业务案例不能直接进入通用发行包。

### 分层验收

| 层级 | 判定对象 | 最低要求 |
| --- | --- | --- |
| 包与安装 | 文档、脚本及安装结果 | 元数据正确、资源与引用完整、跨宿主安装及升级行为符合声明 |
| 选择与路由 | 请求到 Skill 的匹配 | 应调用时能够识别，易混淆请求不会错误扩大任务，显式调用得到尊重 |
| 任务行为 | Agent 的实际成果与动作 | 关键行为正确、有效能力保全、授权边界守住、结果陈述真实 |

格式测试不等于行为评测；执行了脚本不等于真实业务通过。现有安装测试继续保留，新增测试针对新行为，不用重复断言固定措辞充数。

### 首个试点：merge

用临时 Git 仓库提供抽象的可运行小程序、若干独立分支、背景材料及隐藏验收。仅给任务目标与约束，不指定 Git 操作顺序。可先采用四类最小任务：

- 独立能力交叠：一方增加新的输出能力，另一方改变共用内部实现；最终原有与新增能力都可从公开入口使用。
- 自动合并的语义回归：双方分别改变实现和注册或调用契约，文本可自动合并但能力不可达；最终须发现并修复行为损失。
- 连续集成：目标已经保留另一分支的能力，后合入的旧分支改变同一上下文；最终不得覆盖前面成果，也不得重复副作用。
- 有意替代与关键歧义：有明确替代依据时保留行为而不复活旧实现；必要依据缺失时，合理调查后保留成果并提出具体裁决问题。

每项任务由独立验收定义判断最终行为。检查公开入口、输出与副作用，必要时核对有意废弃的能力和 Git 状态；不能只验证源代码里仍有函数或通过 Agent 修改后的测试。评测夹具和验收存放在 Skill 外，Agent 无权修改评分基线。

另有通用硬约束：没有提交或外部写入授权时不越权，不破坏既有未提交内容；行为评测在无生产凭据、无发布权限的隔离环境执行。记录模型、宿主、版本、Skill 内容摘要、输入、动作证据、产物和评分，不把历史对话或无关项目数据带入。

相同模型与工具条件下对比无 Skill、已发行版本和候选版本。先做少量重复，报告逐项结果与波动；功能保全与授权是首要指标，成本和时长其次。新版本若出现关键回归则不发布；样本不足只能说明试点结果，不能声称通用效果提升。人工兜底既有正例也有反例，避免把一律停下当成安全通过。

## 落地顺序与完成标准

1. **统一职责与内容契约**：优先修订 require/design/coding/release 的硬性流程耦合，明确 test 与 business-test 的分工；以能独立处理任务、不会隐含扩大范围作为完成标准。
2. **建立 merge 行为评测试点**：先让旧版暴露真实失误，再评估候选改进；以可复现、能区分功能丢失与有意替代、能检查越权为完成标准。
3. **完善分发保障**：将资源和内容静态校验纳入发布，并实现安装基线与本地修改保护；以安装、冲突、资源删除及失败恢复测试作为完成标准。
4. **按证据扩展工具能力**：在真实任务中评估诊断和维护需求；有重复价值再新增 Skill，有宿主分发需求再加插件清单，不预建 hooks 和常驻状态系统。

首轮只聚焦一个可评测的纵向切面。每批改动在发行源完成，验证后再同步安装副本；Skill 内容改变不自动触发提交、推送或发布。


## 首批实施记录（2026-10-23）

已在源码完成职责与内容契约改造：require/design/coding/release 可独立处理充分明确的任务，不把文件存在当作资格；test 与 business-test 分离策略和详细 Case；review 默认只读、基线及风格由项目事实决定；change 覆盖实现与证据失效范围；knowledge 聚焦当前任务；merge 继续以功能保全为核心。模板同步裁剪为表达参考。business-test 入口按模式导航，执行与 Case 协议保留在按需 references 中。

新增包内元数据和引用完整性测试；发布脚本的 pytest 显式使用源码，避免安装的旧发行版冒充本次受检对象。未改变版本号或发布。

`evals/merge/` 已提供隔离任务准备、独立黑盒评分及自检。候选 Skill 实际运行两个单轮任务：自动合并语义回归任务由 Agent 保全旧、新能力并通过独立验收；关键歧义任务保留原状并请求裁决，保持 manual。结果与限制保存在 `evals/merge/results/2026-10-23-pilot.json`，不将其描述为旧版/新版对比或通用效果提升。

Skill 安装新增宿主目录级版本与 SHA-256 基线：冲突预检全批停止，未修改的资源可更新，修改过的资源得到保留；受管理且未修改的废弃资源可清理，自有文件不受影响。逐文件原子替换与基线最后写入允许失败后重试，不提供跨文件事务或并发安装锁。Skill 冲突时不先写模板或配置。

文档校验脚本区分 Case 定义和运行报告，不再要求规范定义携带实际结果；补充了定义、报告、跨 Case 及代码围栏的独立结构测试。

尚未实现：完整触发测试、多模型多轮版本对照、模板修改保护、故障诊断和维护工具扩展。文档模板仍会覆盖同名文件，README 警示继续有效。后续按证据推进，不因本批完成就声称整体架构目标已完成。


首批本地验证：54 项自动测试通过，覆盖安装与修改保护、四种宿主 CLI、定义/报告结构校验、merge 夹具与独立评分，以及包内元数据和引用完整性。10 个 Skill 格式与通用性扫描通过。Codex 工作区副本和未被定制的五个模板已同步，发行版本号仍为 0.1.6，本批未提交、推送或发布；这些状态不是新版发行结果。
