# IssueKit 分支与工作区清理

判断哪些独立工作现场已经失去用途，在实际授权范围内回收，并保留可核查的历史与恢复条件。清理不是合并、提交或发布，不用自动提交、推送或重写分支历史来制造“已完成”。

## 先确定主分支与任务目标

1. 确认实际仓库、主工作区与 Git common directory；多仓逐仓判断，不把工作区根目录当作 Git 仓库。读取项目规则、已有清理记录和相关任务背景。
2. **先确定主分支，再判断候选是否过期。** 交叉核对用户指定、项目约定、远端默认 HEAD 和真实集成/发布配置。远端默认分支是线索，不自动覆盖项目明示约定；来源冲突时说明证据并保留受影响对象。
3. 区分正式主分支、长期集成分支、区域/版本发布线和任务最终目标。多基线项目应为每项任务确定实际目标；upstream、分叉点、命名和某个包含该提交的分支，都不能单独证明目标归属。
4. 刷新需要的远端跟踪信息并固定本次比较的目标 SHA；优先使用已核验的新鲜远端引用。无需为扫描执行 pull、merge、rebase 或切换用户工作区。查询失败或只有旧缓存时标注时效，不把旧数据当作最新结果。
5. 汇总保护对象：用户指定分支、主工作区、仍有用途的集成/部署现场、锁定对象及正在使用的任务。不能硬编码 `main`、`global` 或默认将所有 `feature/*` 都视为一次性分支。

## 判断是否仍有独立价值

- 先找任务完成、撤销或替代的证据：Issue/PR/MR 状态、合并记录、有效目标与后续用途。年龄、最后提交日期、目录 mtime 和名称只用于筛选与排序，不单独证明过期；最近使用还要考虑未提交文件、编辑器、进程和任务现场。
- 将“**已交付**”与“**可恢复**”分别判断。提交已被任意远端引用包含，只能支持可恢复性，不能证明已合入任务目标、已经发布或不再需要。用户明确放弃任务时可按该取舍处理，但记录原因。
- 先查相对任务目标的祖先关系；遇到 squash、rebase 或 cherry-pick 时结合内容差异、补丁等价和 PR/MR 证据判断。不同提交 ID 不必然代表有未交付功能；祖先关系也不能证明功能未被随后撤销。证据不足就保留或列为待确认。
- worktree 与分支分别决定：目录是否仍需存在、分支是否仍需保留是两件事。允许移除 clean worktree 而保留分支，不因清理目录自动删分支。
- 分别检查已提交的独有内容和未提交现场：暂存、未暂存、未跟踪、重要 ignored 文件、子模块、detached HEAD、合并/rebase 等中间态。`clean` 不等于没有 ignored 配置；远端没有分支也不等于本地没有成果。
- 对象分为：可回收、需归档后回收、保留/待确认。dirty 和仅本地提交不自动销毁，也不因此永久堆积；有归档授权时保全后回收。不得把“有备份”自动解释为销毁或停止仍在使用的工作现场的授权。

## 清理前必须输出清单

在任何目录移除、归档搬移、登记回收或分支删除前，先落盘计划并在对话展示：

| 对象（仓库、绝对路径、本地/远端分支） | 用途 | 最后提交/活动线索 | 目标基线与内容状态 | 拟执行动作 | 理由、风险与恢复条件 |
|---|---|---|---|---|---|

同时说明主分支与目标 SHA、保护范围、未提交/独有内容、是否涉及远端。保留或证据不充分的条目单列，不能只列总数。大量条目可给出完整记录链接并在对话概括，但用户必须在执行前能查看完整清单。

- 用户只要求“看看哪些能删”“调研”或“列出候选”时，只交付计划。
- 已明确要求清理且候选符合已有授权时，展示具体计划后继续执行，无需再为同一范围重复确认。
- 放弃未保存内容、无法验证的备份、仍活动的现场或新增远端目标不在当前授权内时，先完成独立且安全的部分，再说明具体缺口、已准备的方案及需用户决定的动作。
- 运行记录按 [记录与查询约定](references/records.md) 保存。每次生成唯一 run ID，实际工作目录、主分支和归档路径变化不应导致历史记录丢失。

## 按授权执行

### 默认仅本地

- 默认只回收本地 worktree、失效登记与本地分支。`fetch --prune` 仅刷新/回收本地远端跟踪引用，不是删除服务器分支；记录两者差别。
- 用 Git 原生命令回收 worktree，移除前检查完整状态、HEAD、分支归属、锁和活动用途。删除本地分支前检查其他 worktree 是否仍引用它，以及是否存在需要保留的提交。优先普通安全删除；不能只因 `branch -d` 拒绝就升级为 `-D`，须有目标集成或已授权且验证有效的恢复证据。
- `worktree prune` 只处理失效登记，不判断任务是否结束；目录失联、移动、未挂载与真正废弃要区分，尤其不得遗失登记中的 index、合并状态或 detached 提交。
- 操作前复核计划对应的路径、HEAD 和状态，使用可用的条件更新保护引用；对象发生变化时跳过并更新记录。不要通过批量 force 或重试覆盖并发变化。

### 归档后回收

- 归档在所有候选之外的稳定路径。保存完整工作文件（含需要保留的未跟踪与 ignored 文件）、提交版本、暂存区和必要的 worktree 元数据，以及原路径与恢复映射；不用仅一份 diff 冒充完整现场备份。
- 删除唯一引用前先建立可验证的恢复入口；detached 提交同样需要保留。仅存在于原仓库的恢复 ref 不等于独立备份。需要脱离原仓库恢复时，使用包含所需对象的 Git bundle 或等价备份并验证依赖完整性；保留文件备份以覆盖 Git 对象库之外的内容。
- 先验证归档内容与恢复引用，再解除 worktree 登记或删除分支。涉及仅存内容的恢复保证时应作隔离恢复检查；未验证的能力写为限制，不宣称无条件可恢复。
- 记录归档是移出工作区、压缩保留还是物理删除。移出目录不能报告为已释放磁盘空间；不得擅自加归档过期删除任务。

### 用户明确要求同时删除远端时

- 把远端仓库、完整分支 ref、实际 SHA、任务/PR/MR 状态、共享用途和恢复条件加入执行前清单；“清理”“继续清理”“删分支”本身不扩展默认本地范围。
- 明确授权已覆盖本次远端对象时继续，不重复索要许可；只授权了本地或远端目标含糊时，完成本地可执行部分并要求澄清远端范围。
- 尊重服务端保护和其他人的活动；复核后优先使用带预期旧 SHA 的条件删除（远端 lease 或等价能力），远端有新提交就跳过，不重试无条件删除。回读服务器 ref 确认实际结果，不能把 fetch 缓存或请求已接受当作已删除。
- 第三方工具、hooks 和默认设置不能绕过范围：自动 push、删除远端、自动提交、清理服务或环境都需符合当前授权；不因引入工具而隐含执行。

## 清理结果与历史查询

- 每完成一项动作立即记录实际结果、前后版本及恢复位置，失败/跳过也要记；中断保留已完成动作，不能等最后一次写日志。
- 收尾核对 worktree/分支前后数量、保护对象、当前工作区、失效登记、归档与恢复引用。涉及远端时回读实际服务器结果。记录部分成功、失败与中断，计数区分真实目录、登记、本地分支和服务器分支。
- 在稳定目录保存结果与索引，并在最终回复提供链接、run ID、实际动作和剩余项。清理记录是本任务的必需交付，不能只存在于聊天或 `/tmp`；记录不成则如实标注结果不完整，停止追加删除并先恢复记录能力。
- 用户查询历史时，先按仓库、日期、路径、分支或 run ID 检索已有记录，再回答何时、为何、执行了什么及如何恢复。明确区分历史快照与当前状态；查询历史不执行新清理，缺失记录不补造事实。
