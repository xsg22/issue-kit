# IssueKit 测试策略

帮助开发者判断风险在哪里、应验证什么、在哪层验证以及什么结果才算正确。交付与任务规模相称的测试策略、覆盖关系和关键预期；本工具不以生成大量用例衡量完成。

## 输入与事实

用户可提供 Issue、需求描述、变更范围或代码版本。需求和约束足够明确即可开始，不要求先存在技术方案或特定文件。复用相关项目约定、知识摘要、有效需求和设计，结合实际代码、调用方与现有测试核对影响；资料缺失时主动调查，区分事实、假设和未解决歧义。

需要写入 Issue 时，按 `.issuekit/config.yaml` 的 `issues_dir` 定位；现有 `.issuekit/templates/test-plan.md` 可作为表达参考，不要求补齐无关章节。没有 Issue 也可直接交付策略。

## 判断原则

- 从验收标准和有效业务意图确定预期，代码用于理解实现与观测方式，不能用当前错误行为改写预期。
- 同时评估新增行为、仍有效的原有能力及调用方；改动小不代表影响小，优先关注共享契约和失效后果。
- 依据风险选择单元、契约、集成、真实业务或客户端验证层级，优先复用已有有效覆盖；避免在多层重复维护同一份详细 Case。
- 说明关键输入、边界与可观察结果，涉及状态或副作用时明确禁止变化的不变量。并发、重试、权限、数据完整性、兼容和外部依赖失败按实际风险纳入，不机械穷举。
- 可测试性问题先说明其妨碍验证的原因和最小建议，不借制定测试方案扩大为重构实施。
- 需求冲突只阻断依赖它的预期，其余范围继续；能够依据有效契约裁决时自主判断，关键歧义不足以裁决时带证据请人工确认。

## 交付与门禁

交付应能关联需求或风险、受影响能力、已有/待补覆盖、验证层级、关键预期及优先级，并说明执行所需的版本、环境和能力条件。可用覆盖矩阵或简短清单表达，不强制脑图或固定报告格式。

每个关键验收点应有覆盖或明确的缺口/不适用理由。既有测试只有断言仍有效、范围匹配时才可复用；测试存在不等于已执行。计划中的检查不得写成通过结果，已有运行证据应注明受检版本、范围及限制。

详细可执行业务 Case、Fixture、Readiness 和逐轮结果由 `$issuekit-business-test` 维护，以稳定 Case ID 引用，避免在策略文档再复制一套。若用户已经要求生成详细 Case，可直接衔接该工具；不得因此隐含授权外部写入、代码修复或完整开发周期。
