# 需求分析

帮助开发者明确“应实现什么、为什么做、如何判断成功”。交付可供产品与开发共同确认的需求契约，不代替技术方案设计。

## 输入与事实

用户目标、已有 Issue、讨论、图片和当前行为都可以作为输入；不要求先具备指定文件或完整知识库。没有明确目标时，先从当前任务上下文寻找，仍无法确定再询问。

复用项目约定、相关知识摘要和已有需求，针对本次目标核对代码、配置及可访问的运行证据。资料与实现不一致时区分“当前事实”和“期望行为”，不能把现有缺陷直接当成新需求的规则，也不能将旧文档当作已确认事实。

## 判断原则

- 说明背景、受益者、当前行为、目标行为与成功条件；区分必须完成、暂不处理和仍需确认的范围。
- 保全仍有效的业务意图。涉及既有能力的删除、缩减或替代，应找到明确依据并呈现用户影响。
- 围绕行为识别参与者、操作、数据、状态、权限与约束；按风险考虑正常、异常、重复操作及恢复等边界，不机械套用全量检查表。
- 验收标准应描述可观察结果；需要数值阈值时标明来源或待决策状态，不为显得可衡量而编造数字。
- 自主完成资料整理和表达选择。影响业务规则、范围、外部契约或验收结论的歧义，先调查已有依据；无法裁决时提出聚焦问题，不以行业惯例替用户做关键决定。独立可明确的部分继续推进。

## 交付结果

按任务规模输出需求摘要、用户流程或故事、范围、边界、验收标准、关键风险及待确认决策。面向产品与业务方使用业务语言；技术证据只作为必要的可追溯依据，不让源码细节淹没需求。

已有 Issue 就更新原有材料，避免重复创建。需要新建 Issue 时遵循项目的标识规则；无约定可使用 `{TYPE}-{YYYYMMDD}-{short-description}`，类型为 `FEAT`、`BUG`、`OPT` 或 `HOTFIX`，并避免重名。

需要落盘时读取 `.issuekit/config.yaml` 的 `issues_dir`（默认 `issues`），使用现有 Issue 目录与 `.issuekit/templates/requirement.md`（如有）；缺模板不阻断分析。模板按适用范围裁剪，图表只在有助理解时使用。

## 完成门禁与边界

- 当前行为与期望变化有事实依据，需求范围与验收标准一致；推断和待确认项没有伪装成已确认规则。
- 关键歧义未决时，交付可用草案并说明具体决策点、影响和建议，不宣称需求已经确认或可以直接实施。
- 需求分析不隐含切分支、拉取、提交、推送或线上写入授权。不因创建 Issue 文档而自动改变仓库基线。
- 报告实际产物、重要结论和剩余问题。后续可以直接设计、实现或继续澄清，无需强制执行其他 Skill。
