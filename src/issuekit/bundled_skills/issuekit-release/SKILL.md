# 发布准备与交付

帮助开发者判断“当前版本是否具备交付条件”，交付可核验的发布结论、说明和已授权动作。可以在准备阶段进入，不要求代码已提交或全部验证已完成。

## 输入与事实

依据用户指定目标、实际分支或提交、变更、需求意图、设计决策和验证记录工作。既有 Issue 文档与讨论可复用；缺少某个文件不阻断调查，也不能因此跳过验证门禁。

核对本次仓库、源版本、实际目标基线和交付范围；基线来自用户要求、PR 或项目真实约定，不硬编码分支名。区分待提交内容、已提交变更、远端状态和已部署版本，不把它们视为同一对象。

## 交付判断

- 解释具体行为变化、原因和受影响人群，核对实际实现与已确认目标、设计调整及已知依赖。未纳入范围的改动单独说明，避免把无关工作一起交付。
- 汇总功能、接口、数据、配置、依赖和运维变化；已有材料中的需求或方案变更与实际提交相互核对、去重，不能只复制初始计划。
- 验证证据应说明对象与版本、执行内容、实际结果及限制。`test-plan.md` 只说明计划验证什么；执行日志、测试报告和真实结果才能支持通过结论。关联 Case 时沿用既有标识，避免另建重复记录。
- 版本或依赖变化后重新评估受影响证据的适用性。说明未执行、失败及基线已有问题，不能把过期 CI、其他版本测试或功能分支测试当成最终交付证明。
- 按变更风险核对部署依赖、兼容窗口、迁移与配置顺序、可观测性、发布后验收、恢复条件及责任边界。数据不可逆或无法无损回滚时明确限制与替代恢复方案。

## 产物与动作范围

发布说明应让未参与讨论的人看懂问题、最终行为、影响范围、验证状态、必要部署事项和恢复方案。细节与风险相称，不为无配置或迁移变化的修复编造运维步骤。

需要落盘时复用 `.issuekit/config.yaml` 的 `issues_dir`（默认 `issues`）、原有 Issue 与 `.issuekit/templates/release-note.md`（如有），通常写为 `release-note.md`。不存在的文档不要生成虚假引用。

准备说明、提交、推送、创建 PR、合并和部署分别核对是否在本次明确授权中。按已有授权把必要工作完成，不自动串联所有动作，也不重复确认已授权事项。用户要求创建 PR 时完成该动作所必要的推送可按上下文判断；授权或目标不明确且会影响共享状态时先确认具体动作。

获准创建或更新 PR 时，使用实际目标基线，标题与正文围绕最终变更；说明真实验证结果和剩余风险，遵循仓库模板。只有远端返回成功并能核对结果，才报告对应动作完成。

## 完成门禁与兜底

- 交付版本、变更范围与目标可追溯，需求和设计偏差得到解释；不能因文档齐全就认定可以上线。
- 对关键验证、依赖或恢复条件不足的情况，给出具体缺口及影响。能补足的先补足，必须人工裁决时提供证据、选项和建议；不能静默降低标准。
- 发布准备可以完成但交付条件尚未满足，必须分别报告。无证据不声称测试通过，无执行不声称已发布。
- 完成后报告实际分支或版本、文档、验证结论及已执行动作；有 PR 或发布结果时给出可核对的位置，保留未验范围与恢复风险。
