# 编码实现

帮助开发者把明确意图落实为完整、可验证的代码。实现方式由 Agent 根据项目事实选择，完成标准是目标与工程约束得到满足。

## 输入与事实

用户要求、已有代码、讨论及有效设计决策都可作为依据，不强制先生成需求或技术方案文件。按任务需要复用项目约定、知识摘要及现有测试，并核对材料与当前实现是否一致。

在修改前明确本次代码范围、实际分支与已有工作成果。识别受影响的调用方、接口、数据、配置、异步链路、测试和文档；不能只完成一个局部函数便宣称功能完成。

## 实现原则

- 复用项目现有能力与惯例，以最小完整变更实现目标。保留边界校验、错误处理、权限约束及避免数据丢失的保护，不为省代码降低可靠性。
- 保全仍有效的既有能力，包括此前其他改动引入的入口、配置和必要副作用；删除或替代须有明确依据或等价承接。
- 遵守有效技术决策，但不机械实现已证伪的方案。发现设计与代码、需求冲突时调查原因：可自主决定的实现调整说明依据并更新相关材料；改变业务规则、范围或外部契约需要足够依据，否则提出人工决策点。不要先扩散有问题的实现再统一补救。
- 对关键业务歧义先追溯需求、历史和调用契约。不能以“合理默认值”代替缺失的业务决定；继续完成不依赖该决定的部分。
- 数据迁移脚本、模型、映射、接口和配置保持一致。编写 DDL 或操作说明不等于获得执行授权；编码任务不自动执行线上 DDL、DML、配置或部署变更。
- 同步受影响的测试与文档，避免无关清理和扩大范围；保护其他任务的未提交内容。

## 验证与交付

对照需求意图、有效设计决策和当前接口契约检查完整性，而非仅对照文件清单。按风险选择编译、静态检查、针对性测试或真实链路验证；新行为、修复缺陷及可能受损的既有能力都应有相称的证据。

验证失败时区分环境阻塞、基线已有缺陷和本次回归，分类须有依据。修复本次引入的问题，无法执行的验证标明原因与影响，不通过删除校验、弱化断言或仅更新快照来掩盖回归。

报告实现了什么、影响哪些能力、在哪个分支修改、运行了哪些验证及其结果。证据绑定实际受检版本或工作区状态；仅完成代码阅读、制定测试计划或编译成功，不代表业务验收通过。

已有 Issue 时复用 `.issuekit/config.yaml` 的 `issues_dir`（默认 `issues`）与相关材料，记录有意义的设计调整和剩余决策，不为小任务强制补写整套文档。

## 完成门禁与授权

- 本次目标和关联改动完整，需求、实现与有效契约无已知偏差，既有能力没有无依据的缩减。
- 验证结论真实且适用于交付版本；已知失败、未验范围和关键未知被明确披露，不虚报完成。
- 尽力调查、实现和修复后，仍需人工决定的事项应携带证据、选项、建议和影响，保留已完成成果。
- 代码修改不自动授权提交、推送、创建 PR 或外部系统写入；遵守本次已有明确授权和项目约定，不重复索要已经授予的权限。
