# IssueKit 项目知识

帮助开发者及后续工具理解当前系统如何工作、哪些边界和约束与任务有关。知识摘要提供导航和证据，不能代替实际代码或把历史快照当作当前事实。

## 范围与输入

根据用户目标选择最小充分范围：具体任务聚焦有关链路，指定模块覆盖其必要依赖；明确要求全库知识时才做全库梳理。请求仅为泛泛建立知识且没有当前任务时，可先建立项目概览，再按实际需要深入，不默认扫描所有 API、依赖或 Git 历史。

复用项目规范及 `.issuekit/knowledge/` 中有关摘要，优先增量更新。已有摘要无需全部加载；事实可能变化且影响结论时，核对当前代码、配置和版本。无知识目录不阻止直接分析。

## 内容取舍

按任务需要梳理：

- 项目定位、技术栈与真实入口。
- 模块职责、依赖方向、关键调用链、生命周期与横切约束。
- 对外契约、数据模型、状态与必要副作用。
- 外部服务、配置来源及工程约定。
- 未确认事实、已知风险、适用条件与后续检索入口。

以真实结构描述系统，不强行套用分层或设计模式。代码规模、贡献者、全接口清单和图表仅在有助于当前目标时生成；不要为填模板而收集。区分显式规范、代码中观察到的惯例与建议，不能把观察到的模式升级为强制规则。

必要的隐藏配置和项目规范可按权限核对，不因隐藏文件一律忽略；不读取或传播无关凭据，摘要仅保留配置键和来源等必要事实。查询数据库或其他环境前核实项目、环境和数据源身份，无法确定时记录缺口，不混入别的环境信息；本工具不授权外部写入。

## 交付与完成门禁

交付应说明范围、实际版本/采集时间、关键结论、证据位置和未知点。入口与调用关系应能回到代码核验，推断有明确标记；未扫描范围不能声称已覆盖。

需要持久化时，沿用 `.issuekit/knowledge/` 下适用的概览、架构、接口、数据、集成与约定文件；模块摘要放在 `.issuekit/knowledge/modules/`。只创建或更新确有内容价值的文件，保留其他任务的知识与未提交成果，不把局部结论写成全局规则。

摘要过时或证据冲突时，先查当前实现和有效约定，更新受影响内容并说明适用范围。仍无法确定且影响后续工程决策时，给出具体证据缺口与人工确认点；其余已确认知识可以先交付。
