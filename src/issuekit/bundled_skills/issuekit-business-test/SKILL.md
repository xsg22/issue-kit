# IssueKit 真实业务测试

## 定位

本 skill 是 `issuekit-test` 的执行增强层：`issuekit-test` 负责回答“需要测试什么”，本 skill 负责回答“如何落地、如何准备数据、当前机器能验证到什么程度、如何保存证据”。

测试用例本身尽量与环境无关；业务规则来自 Issue 和 `.issuekit/testing/`，接口、数据模型、日志和异步链路来自当前代码。执行时再绑定 `local`、`pre` 或 `prod`。

本 skill 不内置任何具体业务领域。订单、库存、权限、审批、任务、消息、异步工作流和资源交付只是可支持的领域类型；具体业务规则必须放在项目自己的 `.issuekit/testing/business-domains/` 中。

核心链路固定为：

```text
需求规则 -> 状态模型 -> 测试数据 -> 真实用户操作 -> 接口结果
  -> 数据库变化 -> 日志/消息/异步收口 -> 证据判定 -> 回归循环
```

## 使用模式

- `design`：读取需求、方案、代码和项目测试知识，生成详细测试用例，不执行外部写操作。
- `prepare`：根据已确认的执行上下文准备测试账号和数据库状态，保存前后快照、变更和回滚信息。
- `execute`：执行用户操作或接口流程，采集接口、数据库、日志、异步任务和最终资源证据。
- `regression`：针对已修复或受影响的 Case 重复执行，并对比前后结果。

未明确模式时默认使用 `design`，不自行准备数据或执行真实业务。

一轮执行必须覆盖当前测试清单中的全部 Case。优先级只影响调度顺序，不能作为跳过低优先级用例的理由；每条 Case 最终都必须有明确结果。

## Case 维护与文件边界

- 一个 Case ID 只对应一个规范定义文件；总览只保存基线、覆盖矩阵和指向定义的索引，不再复制简版用例或真实结果。Fixture 定义、问题单、每轮执行报告和原始证据分目录保存。
- 新增 Case：先定位需求条款和现有 Case，决定是否为独立状态变体；分配未使用过的 ID，写独立的前置状态、步骤、精确断言、Fixture 引用及变更原因，再更新索引、覆盖矩阵和 Fixture 映射。不能只在报告末尾追加新 Case。
- 修改 Case：在定义文件写明变更日期、需求/问题来源、旧规则到新规则的差异和受影响 Case；已执行过的预期不得回写历史报告。调整断言或行为口径时提升 Case 修订号，下一轮报告必须记录执行时的修订号与 Git commit。
- 删除/合并 Case：不得静默删除或复用 ID；先证明需求废止、重复或被哪个 Case 覆盖，再标记 `RETIRED`/`DEFERRED`，记录原因、替代 ID 和历史证据位置。退休定义仍保留，执行范围由索引的状态决定。
- 每轮执行仅写独立的 `test_run_id` 报告，逐条记录 `case_id + revision + commit + fixture_id`、结果和证据，不把 `actual` 或 `PASS/BLOCKED` 写进规范定义。历史报告只追加勘误，不覆盖原记录。
- 固定脚本：需要可重复验收的项目为每个 READY Case 维护同 ID 的执行脚本；使用共享驱动处理认证、环境、数据源、证据归档，业务 Fixture、动作与断言由该 Case 的固定脚本定义。变更用例时同步变更脚本和修订号；禁止在重跑时临时由 AI 解释文字、拼接 SQL 或让缺脚本的 Case 假装通过。未完成脚本的迁移用例保留 NEEDS_REFINEMENT，运行器拒绝执行而非创建空脚本。
- 迁移旧文档时先列出所有 ID，逐项核对迁移前后 ID 集合和数量，保留原断言及既有未提交修改；未知来源和缺失断言标记 `NEEDS_REFINEMENT`，不得推断为可执行。新增、修改、退休、迁移后均检查唯一 ID、索引链接、需求覆盖、Fixture 关联和报告引用。

### 通用门禁与项目实现边界

- 本 skill 只规定执行前后必须可核验的条件，不规定账号池文件格式、手机号范围、登录实现、数据库驱动、脚本语言或项目目录布局。账号注册/租用、获取会话、构造业务 Fixture、Case 固定脚本及批次运行器由项目 `.issuekit/testing/` 实现；不得把某个项目的账号、密钥、接口或 SQL 写进通用 skill。
- 批次执行前，项目实现必须输出可核验清单：明确环境及实际被测版本、服务和数据库身份、Case ID@revision、每条 Case 的账号/租约与前置状态、凭据来源、写入范围、复位或保留策略。校验会话归属与 UID/环境一致，校验服务实际数据源而非仅比较上下文文件中的声明；同一可变主体不能并行复用。
- 对每条 Case 做前置门禁：缺账号或过期凭据、服务未启动、数据源不明、Fixture 不符、缺写入授权或固定脚本时，标记具体的 `BLOCKED`/`NOT_RUN` 原因，禁止发起有副作用的业务动作；不得临时用其他账号、连接或手工生成步骤绕过。一次性前置状态用新主体或已审查的重置方案，不能在旧账号上假装首次运行。
- 固定脚本必须真正向声明的服务发起请求，并在需要时回读数据库、日志或异步事实；单测、Mock 服务和脚本语法校验只证明脚本质量，不计入真实业务验收。运行报告分别记录“脚本检查”和“真实环境执行”。批次可以显式选取部分 Case，但须报告选取范围、遗漏的 ACTIVE Case 和 `INCOMPLETE_EXECUTION`，不得称作全量验收。

## 标准工作流

按以下阶段执行，不得跳过事实收集直接编写结果：

1. **Discovery**：读取需求、方案、知识库、代码、配置、数据库模型和已有测试。
2. **Modeling**：建立参与者、实体、状态机、业务规则、输入边界和副作用模型。
3. **Generation**：生成需求覆盖矩阵、详细 Case、测试数据配置和断言。
4. **Readiness**：探测目标环境、认证、接口、数据库、日志、异步查询和数据写入能力。
5. **Planning**：生成批次级 Fixture 计划，把全部 Case 映射到独立或可复用 Fixture。
6. **Preparation**：按已验证的 Fixture 计划初始化数据，保存并校验快照。
7. **Execution**：执行真实用户流程或明确标注的接口模拟。
8. **Verification**：按同步响应、数据库、日志、异步、最终资源五层证据验证。
9. **Verdict**：根据证据完整度判定结果，不用单个接口响应代替整条业务结论。
10. **Regression**：修复后仅重跑受影响 Case 和关键关联 Case，保留每轮证据。

## 状态变化验收硬规则

每条 Case 都必须是一个可判定的状态转换协议，不能只描述“执行某操作后应正常”或“资源不应超扣”。生成 Case 时必须同时回答：

1. **执行前是什么状态**：用户/租户、业务实体、权限、资源余额、窗口、订单或任务状态必须写成可查询的字段和值。
2. **用户能看到什么变化**：明确操作前后的页面状态、接口字段、业务提示、可继续执行的动作和不可执行的动作。
3. **系统实际保存什么变化**：明确数据库实体、状态字段、账本流水、数量增减、时间窗口、来源和关联 ID 的 `before/prepared/after_response/after_async` 值。
4. **中间状态是什么**：涉及预占、处理中、异步投递、确认、释放或补偿时，必须写出请求后但最终收口前的状态。
5. **哪些变化被禁止**：明确不得变化的字段、不得创建的任务/订单/交付物、不得跨窗口结转的资源，以及不得出现的负数或重复流水。
6. **变化量如何计算**：对分钟、次数、金额、库存、配额等数值写出精确公式、单位、舍入规则和最终 delta；不能使用“适量”“按实际处理”“不超扣”等模糊表述。

### 状态变体选择规则

- 先比较不同用户状态、权限等级、资源来源、生命周期阶段和输入边界是否改变预期结果、状态转换或数据断言。
- 有差异时必须拆成独立 Case，或明确使用参数化 Case，并为每个变体提供独立 Fixture 和断言。
- 无差异时可以选择一个代表性变体，但必须记录比较过的变体、确认无差异的字段、代表该变体的理由，以及未单独执行的变体。
- 不能因为代码实现相似就认定业务无差异；差异判断优先来自需求，代码只用于补充查询和操作方式。
- 任何不同的前置状态都必须映射为 `before -> action -> intermediate -> after`，并区分“用户可见状态”和“系统状态”。

### 资源/账本 Case 的最小断言

涉及可变资源时，Case 至少要写明：

```text
用户可见状态：操作前可用/不可用；操作后可用/不可用；展示的剩余值和提示
系统状态：实体状态、窗口状态、来源、账本流水和关联业务 ID
精确变化：available/granted/consumed/reserved 的 before -> after 与 delta
禁止变化：负余额、跨窗口结转、跨类型扣减、重复消费、无业务输入的占位任务
```

如果实际结果与任一需求断言不一致，必须列出字段级差异并判定 `FAIL`；不能用“主流程成功”覆盖资源账本或状态机失败。

## 必须先读取

1. `.issuekit/config.yaml`、`.issuekit/knowledge/`。
2. `.issuekit/testing/config.yaml`、`business-domains/`、`evidence-sources.yaml`、`capabilities.yaml`（存在时）。
3. 当前 Issue 的 `requirement.md`；`technical-design.md` 存在时作为辅助材料读取，不存在或不完整时从真实代码和运行配置补齐。
4. 需求涉及模块的实际 Controller、Service、DAO/Mapper、任务编排、错误码和测试代码。

同时建立三份事实清单：

- `REQUIREMENT_FACT`：需求明确要求；
- `CODE_FACT`：当前实现实际行为；
- `UNKNOWN` / `CONFLICT`：无法确认或需求与实现不一致。

不能把行业经验、类名或猜测当作实现事实。

## 第一准则：需求决定预期

测试通过标准必须以用户确认的、当前有效的需求文档及验收标准为准；需求版本/更新时间不明确时，先确认哪一版生效。技术方案、接口文档、代码、数据库和测试只用于补充如何调用、如何准备数据、如何观测结果，不得覆盖或缩小需求要求。

- 需求明确、实现与需求冲突：Case 的预期仍按需求写；实际实现不符合时判 `FAIL`，并记录 `IMPLEMENTATION_GAP`。不能把冲突改成“待确认”来避免失败。
- 需求文档彼此冲突或同一文档内部矛盾：逐条引用冲突原文，标为 `REQUIREMENT_CONFLICT`；只阻断依赖该冲突规则的 Case，其余无关 Case 继续生成和执行。
- 需求有明确目标但没有接口字段、错误码、状态字段或数据可观测细节：从批准的契约和真实代码补充映射，标注 `CODE_FACT`；若实现缺少完成需求所必需的行为，仍以需求为 oracle 并判实现缺口。
- 需求本身确实未定义用户可感知规则：可由方案/代码提供候选解释，但必须标 `ASSUMPTION`，不得伪装成已确认需求；仅在多个解释会改变预期结果时阻断该 Case。
- 代码现状永远不是修改需求预期的理由。代码只说明“现在会怎样”，需求说明“应该怎样”。

### 测试用例格式是执行协议

测试用例不是说明性文档，而是执行器输入。定义文件中的每一个 Case 都必须独立包含以下预期字段，不得让执行者从前后文猜；真实执行字段存入每轮独立报告：

1. Case ID、优先级、覆盖标签、需求原文/验收标准 ID；
2. 测试主体角色/适用范围、认证方式、业务实体状态、完整资源状态；具体执行 UID 归属执行报告；
3. `fixture_id`、初始化目标值、初始化前后查询及重置方式；
4. 用户操作步骤，逐步写明接口方法/路径、请求 JSON、具体输入值和异步等待条件；
5. 每一步的预期 HTTP 状态、响应顶层业务码、关键响应字段和值；
6. 数据库 `before/prepared/after_response/after_async` 的表、查询条件、目标字段和精确预期变化；
7. 任务、消息、账本、订单、交易和最终资源的副作用断言；
8. 单一、无歧义的 PASS 条件；

每轮执行报告按 `case_id + revision` 独立记录真实 UID、请求响应、证据位置、预期/实际差异和结论；FAIL 写直接原因，按风险补 5 Why、根因和下一步修复/回归计划。

拒绝使用下列表达作为最终预期：

- “失败或不足均可”“按实现决定”“返回稳定错误”“正确处理”“余额不能异常”；
- 只写业务提示名称，但不写需求规定的实际业务码、关键字段和值；
- 只写“权益正确变化”但不列出哪个窗口/账本字段从什么值变成什么值；
- 只写成功/失败而不写业务状态、订单/任务状态和是否产生副作用。

若需求没有指定错误码但现有公共契约有唯一稳定 code，可以把该 code 作为协议层断言，同时将业务成功/失败标准继续按需求。若代码没有稳定 code，Case 必须明确报告 `MISSING_CONTRACT_ASSERTION`，不能将多个结果并列为可通过选项。

缺失项目测试配置时，可以使用默认结构，但要记录“项目测试知识未初始化”，不能假设数据库表、日志入口或接口路径。

## 生成测试用例

每个业务 Case 必须明确：

- 业务目标和需求来源；
- 用户/操作者状态、业务实体状态和权限状态；
- 具体输入值和边界值，不使用“适量”“约几分钟”等模糊描述；
- 用户操作步骤及对应真实接口；
- 同步接口响应断言；
- 数据库执行前、准备后、响应后、异步收口后的断言；
- 日志、消息、任务、文件或交付物等副作用；
- 幂等、重试、并发、失败和补偿行为；
- 通过标准、失败判断、证据清单和下一步计划。

每个 Case 都必须给出可执行的确定性断言，不能用“合理处理”“按实现决定”“不足或失败均可”等表述。明确具体 HTTP 方法/路径、请求字段和值、外层与业务 code、响应字段和值、任务最终状态、数据库行/字段前后值、账本金额和异步收口条件。若需求没有规定协议码，可用当前稳定契约补充协议断言，但业务结果仍按需求判定。

输出 Case 时只写预期，不在定义中预填 `actual=NOT_RUN`。每轮执行报告必须按冻结的 Case 清单逐项填写独立的 `actual` 记录；未执行填 `NOT_RUN`，不能把全局测试结论代替逐 Case 结果。真实结果区必须有请求/响应、数据库变化、证据位置、预期/实际差异、结论和失败原因；FAIL 原因不能只写“和预期不符”。

需求与代码/配置冲突时，需求仍是通过 oracle；在 Case 中并列记录 `REQUIREMENT_EXPECTATION` 和 `CODE_FACT`，并把符合需求设为通过条件。不能因存在冲突而把 Case 从本轮验收中移除。

### 场景组合规则

针对每个业务规则，至少分析以下维度，并按核心程度裁剪数量：

- 正常路径、替代路径、异常路径和边界值；
- 用户身份、角色、权限和客户端版本；
- 业务实体的每个关键生命周期状态；
- 余额/库存/额度为 0、刚好够、差 1、超过 1 和大量剩余；
- 首次操作、重复操作、幂等重试、并发提交和超时重试；
- 外部依赖成功、拒绝、超时、回调失败和部分成功；
- 同步返回、异步最终状态和最终资源是否一致。

每条 Case 都要给出“执行前状态 -> 用户动作 -> 中间状态 -> 最终状态”。不得只写一句“验证接口是否正常”。

### 测试预言机

每个预期结果必须说明来源和判定方式：

- 需求预言机：用户可感知的业务结果；
- 契约预言机：HTTP/gRPC 状态、错误码、响应字段和兼容性；
- 状态预言机：数据库实体和状态机变化；
- 副作用预言机：消息、任务、文件、通知、账本和外部调用；
- 不变量预言机：余额不为负、同一幂等键不重复、失败不产生成功资源、权限不越权。

如果需求与代码对同一结果不一致，保留需求侧精确预期，同时增加代码现状断言和 `IMPLEMENTATION_GAP` 判定；只有需求本身互相矛盾才标 `REQUIREMENT_CONFLICT`。

路由归属也按需求/API 合同判定：不要因为当前实现中存在特定范围的接入入口，就自行把合同规定的共用接口写成范围限定路径。先读需求中的端点定义和客户端对接合同，再核对实际路由映射。若合同规定共用接口而代码另外暴露范围限定副本，Case 使用合同路径，并另记 `ROUTE_DRIFT`/冗余兼容入口；不以多一个实现入口为由改变规范客户端路径。

### 覆盖模型

为每个需求点生成覆盖标签：`happy_path`、`boundary`、`negative`、`state_transition`、`idempotency`、`concurrency`、`retry`、`dependency_failure`、`data_integrity`、`security`。核心业务至少覆盖正常、边界、失败、幂等和数据一致性；并发、权限和外部失败按风险决定是否纳入。

### 风险和优先级

每条 Case 标记 `P0/P1/P2/P3`，依据用户影响、资金或可变资源风险、数据破坏风险、不可逆程度和回滚难度确定。P0/P1 Case 必须包含数据库和异步证据，否则不能标记完整通过。

### 真实操作规则

优先按真实用户路径描述操作，例如登录、打开功能页面、选择业务对象、提交输入、取消任务、重试操作；再映射到当前代码中的 HTTP/gRPC/CLI 接口。若只能调用接口而无法还原客户端操作，要明确标记为接口级模拟，不得声称完成客户端验收。

### 数值和边界规则

对时长、金额、数量、配额等数值规则，依据项目需求明确阈值、单位、精度和舍入方式，覆盖零值、边界前、边界值及边界后；涉及可变资源时补充不足、刚好满足和有剩余的情况，给出精确预期，不在通用 Skill 中预设业务阈值。

### 契约与实现漂移

分别比对需求文档、接口文档、Controller/DTO、Service、数据库和已有测试。发现路径、字段、错误码、状态或数据口径不一致时，生成 `CONTRACT_DRIFT`，列出各来源证据和当前采用的验证口径；不得静默改写测试预期。

## 执行上下文

`prepare`、`execute`、`regression` 必须由用户或上层流程提供：目标环境、代码分支或部署版本、服务地址、数据库和日志来源、认证方式、测试 UID、客户端版本，以及允许的写操作范围。

禁止根据当前目录、当前分支、URL、历史对话或机器默认连接自行推断目标环境。环境未明确时只能生成用例，不能执行。

测试 Case 不绑定环境；执行报告必须绑定实际环境。必须区分：

- 代码工作区的分支/commit；
- 远程环境实际部署的版本/commit；
- 本次请求实际访问的服务地址；
- 本次查询实际连接的数据库和日志来源。

如果用户要求测试 Pre，但实际调用了本地服务，结果必须标记 `ENVIRONMENT_MISMATCH`，不能作为 Pre 验收结果。

## 能力探测和结果等级

执行前读取 `.issuekit/testing/capabilities.yaml` 和可用工具，标记能力为 `AVAILABLE`、`PARTIAL`、`UNAVAILABLE`、`UNKNOWN` 或 `FORBIDDEN`。

- 缺少核心请求能力、测试主体或无法构造目标场景：`BLOCKED`。
- 接口已执行但数据库、日志或异步证据不完整：允许执行，结果只能是 `PASS_WITH_WARNINGS` 或 `PARTIAL_PASS`。
- 所有关键层级证据完整且断言通过：`PASS`。
- 需求或代码不适用：`NOT_APPLICABLE`。

证据不足不能判定完整 `PASS`，但一般能力缺失也不应阻止可完成的接口测试。

能力门禁采用软门禁优先：

- `BLOCKED`：无法执行核心动作，例如没有接口、没有测试主体、无法构造核心状态；
- `PARTIAL_PASS`：主流程执行了，但关键数据库、日志或异步证据缺失；
- `PASS_WITH_WARNINGS`：核心证据完整，非核心辅助证据缺失；
- `PASS`：需求要求的所有关键层级证据均已验证。

不能因为缺少非核心日志就阻止接口测试；也不能因为接口返回成功就忽略数据库和异步结果。

## 数据准备和证据

数据库写入必须显式记录目标环境、UID、表、条件、旧值、新值、影响行数、回滚方式和是否保留。优先使用业务接口准备数据；只有无法构造边界状态时才使用受控 SQL 或测试数据工具。

### 测试数据准备协议

`prepare` 不是简单执行一条 SQL，必须按以下顺序完成：

1. **确认需求基线**：明确完整的需求文档、需求版本/commit、验收标准和测试 Case 来源；不能使用未确认或混合版本的需求。
2. **确认实现基线**：明确本地实现分支和 commit，或远程部署版本及对应 commit；不能用当前工作区分支自动代替实际被测版本。
3. **读取技术方案（可选）**：技术方案存在时用于理解设计意图；缺失或不完整时记录缺口，必须以真实代码、配置、数据库模型和运行行为补齐，不阻塞初始化。
4. **绑定执行上下文**：生成 `test_run_id`，确认目标环境、服务地址、数据库、测试主体和允许的写操作范围。
5. **选择数据档案**：根据 Case 选择独立账号、租户、业务前缀、幂等键、资源路径和输入文件；不能复用未知历史状态。
6. **准备前检查**：查询测试主体、业务实体、可变资源、未完成任务和同幂等键历史，保存 `before` 快照。
7. **生成准备计划**：逐项列出目标字段、当前值、目标值、准备方式、预期影响行数、回滚方式和残留策略。
8. **执行初始化**：优先调用业务接口；只有业务接口无法构造临界状态时，才允许受控数据库写入。
9. **验证准备结果**：回读全部目标字段，确认实际值等于 Case 前置状态；任一字段或影响行数不符合预期，停止执行，不进入业务操作。
10. **冻结测试状态**：记录 `prepared` 快照和准备操作清单，准备完成后不得再由其他步骤隐式修改前置数据。
11. **执行和收口**：业务操作完成后保存 `after_response`、`after_async` 快照。
12. **处理残留**：按事前确认的策略清理、保留或标记残留，不得猜测性删除。

准备阶段的失败必须单独标记为 `DATA_PREPARATION_FAILED`，不能归因于业务实现；数据准备未通过时，不得执行 Case。

一轮测试必须先生成批次级 Fixture 计划，再执行任何写入。计划至少包含：

- 测试批次和 `test_run_id`；
- 目标环境、服务版本、数据库和写入授权；
- 全部 Case 到 `fixture_id` 的映射；
- 每个 Fixture 的主体、目标字段和值、初始化方式、预期影响行数；
- 主体占用/租用标识和并发冲突检查；
- 复用、复位、清理和保留策略；
- 失败后的停止点和回滚方式。

Fixture 计划没有通过完整需求基线、实现基线、环境校验和主体冲突校验时，只能停留在 `PLANNED`，不能进入 `APPLIED`。技术方案缺失或不完整不阻塞，但必须记录为 `TECHNICAL_DESIGN_GAP`，并由代码事实补齐。

每次执行生成唯一 `test_run_id`，至少保存需求/方案版本、代码或部署版本、环境、UID、请求响应、traceId、业务 ID、数据库四阶段快照、日志查询、异步状态、最终结论和限制。

### 数据隔离

测试数据必须尽量使用独立 UID、业务前缀、幂等键和资源标签。并发或异步测试使用唯一 `test_run_id`，禁止依赖“最近一条订单/任务”这种不稳定查询。无法隔离时记录污染风险，不得把其他测试产生的数据归入当前 Case。

### 共享可变资源 Fixture

涉及额度、余额、库存、次数或其他可变资源的 Case，执行前必须把数据初始化到 Case 明确要求的数值，例如 `resource_a=1`、`resource_b=0`，不能使用主体当前碰巧存在的数量。

多个 Case 可以共享同一个初始化 Fixture，但必须满足以下条件：

- Case 之间没有消费、订单、任务或资源副作用，或每个 Case 执行前都能恢复到同一 Fixture；
- 共享 Fixture 有唯一 `fixture_id`，并记录初始快照和复位方式；
- 一个 Case 的成功、失败或残留不会改变下一个 Case 的前置状态；
- 并行执行时不得共享同一可变主体、资源窗口、业务订单、幂等键或外部资源。

如果 Case 会消费可变资源，默认按独立主体或“每 Case 重置”处理；只有明确证明可复用时，才能多个 Case 共用资源余额。

### 等待、重试和超时

异步验证必须定义轮询对象、成功条件、失败条件、最长等待时间、轮询间隔、最大重试次数和超时后的结果。重试请求必须复用原幂等键；查询重试不能触发业务写入。超过等待时间标记 `TIMEOUT` 或 `PARTIAL_PASS`，不能直接判定业务失败。

### 证据完整性

每份证据包含 `test_run_id`、`case_id`、采集时间、来源、查询条件和脱敏状态。证据互相矛盾时保留全部原始结果，标记 `EVIDENCE_CONFLICT`，不能选择看起来更合理的一份。

数据库状态至少采用四阶段快照：

1. `before`：执行前真实状态；
2. `prepared`：初始化到 Case 要求后的状态；
3. `after_response`：接口返回后的同步状态；
4. `after_async`：异步任务最终收口状态。

数据初始化优先走业务接口；必须直接写库时，记录 SQL/工具、条件、旧值、新值、影响行数、回滚方式和是否保留。未确认表结构或字段时禁止猜测写入。

每次执行至少关联：`test_run_id`、`case_id`、UID、环境、代码/部署版本、请求时间、requestId、traceId、订单号/任务号/资源 ID、数据库快照、日志查询和最终结论。敏感 token、密码、签名和验证码必须脱敏。

## 执行循环

真实验收不是一次性运行：

1. 生成并评审 Case；
2. 探测当前机器能力并生成 Readiness 报告；
3. 构造测试批次 Fixture，并为每个 Case 分配独立或可复用的 Fixture；
4. 生成执行计划，标明串行依赖和可并行 Case；
5. 准备测试数据并保存快照；
6. 执行一轮全部 Case，不得因部分 Case 失败而提前结束；
7. 记录接口、数据库、日志和异步证据；
8. 对失败项做 5 Why，区分代码、数据、配置、环境和证据缺失；
9. 批量修复发现的问题；
10. 重新执行受影响和失败的全部 Case，并补跑关联回归；
11. 输出本轮和累计结果。

每一轮必须使用新的 `test_run_id`，不能覆盖上一轮证据。

修复回归时必须记录失败 Case、根因、修复 commit、重新执行的 Case、未重跑的关联 Case 及原因。不能只重新执行成功路径来替代对原失败边界的验证。

每个 Case 的执行结果都必须单独记录：`expected`、`actual`、差异、证据、结论和失败原因。`FAIL` 必须写出可复现的直接原因；复杂失败再追加至少 5 Why、根因、修复建议和回归 Case。`NOT_RUN`/`BLOCKED` 必须说明阻塞条件，不能留空或记成 PASS。

### 并行执行规则

可以使用子 Agent 并行执行相互独立的 Case，但主执行器必须先完成全量 Case 清单、Fixture 分配和依赖图。只有以下条件全部满足才允许并行：

- 测试账号/租户不同，或有可靠的状态隔离；
- 不共享可变资源、库存、业务订单、任务、文件、缓存键和幂等键；
- 不依赖同一个外部限流配额或顺序状态；
- 数据库、日志和业务 ID 能按 `test_run_id`/`case_id` 唯一归属；
- 一个 Case 失败不会改变另一个 Case 的预期前置状态。

无法证明独立时必须串行执行。子 Agent 只能负责已分配的 Case，不能修改其他 Case 的数据或结论；主执行器负责汇总、补跑失败项并确认清单完整。

### 全量完成门禁

执行报告必须包含测试清单中的每个 Case。存在未执行 Case 时，整轮结果不能标记为完成，只能标记 `INCOMPLETE_EXECUTION`，并说明未执行原因和下一步。

- `references/testcase-schema.md`
- `references/test-model.md`
- `references/execution-context.md`
- `references/database-evidence.md`
- `references/preparation-protocol.md`
- `references/data-isolation.md`
- `references/contract-drift.md`
- `references/failure-analysis.md`

## 输出和结束检查

使用项目中的 `.issuekit/templates/business-test-case.md`、`test-readiness-report.md` 和 `test-execution-report.md`（存在时），输出到当前 Issue 目录或 `.issuekit/testing/generated/`，按项目维护规范分开 Case 定义、索引、Fixture 和逐轮报告。不要覆盖已有执行记录；新一轮使用新的 `test_run_id`。

完成后核对：每个需求点都有 Case 或明确不适用；每个 Case 有具体状态、输入、步骤、接口断言、数据库断言和副作用断言；执行上下文未被隐式推断；证据不足已降级；失败用例有 5 Why、修复范围和下一轮回归计划。
