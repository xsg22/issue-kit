## Case 维护与文件边界

- 一个 Case ID 只对应一个规范定义文件；总览只保存基线、覆盖矩阵和指向定义的索引，不再复制简版用例或真实结果。Fixture 定义、问题单、每轮执行报告和原始证据分目录保存。
- 新增 Case：先定位需求条款和现有 Case，决定是否为独立状态变体；分配未使用过的 ID，写独立的前置状态、步骤、精确断言、Fixture 引用及变更原因，再更新索引、覆盖矩阵和 Fixture 映射。不能只在报告末尾追加新 Case。
- 修改 Case：在定义文件写明变更日期、需求/问题来源、旧规则到新规则的差异和受影响 Case；已执行过的预期不得回写历史报告。调整断言或行为口径时提升 Case 修订号，下一轮报告必须记录执行时的修订号与 Git commit。
- 删除/合并 Case：不得静默删除或复用 ID；先证明需求废止、重复或被哪个 Case 覆盖，再标记 `RETIRED`/`DEFERRED`，记录原因、替代 ID 和历史证据位置。退休定义仍保留，执行范围由索引的状态决定。
- 每轮执行仅写独立的 `test_run_id` 报告，逐条记录 `case_id + revision + commit + fixture_id`、结果和证据，不把 `actual` 或 `PASS/BLOCKED` 写进规范定义。历史报告只追加勘误，不覆盖原记录。
- 固定脚本：需要可重复验收的项目为每个 READY Case 维护同 ID 的执行脚本；使用共享驱动处理认证、环境、数据源、证据归档，业务 Fixture、动作与断言由该 Case 的固定脚本定义。变更用例时同步变更脚本和修订号；禁止在重跑时临时由 AI 解释文字、拼接 SQL 或让缺脚本的 Case 假装通过。未完成脚本的迁移用例保留 NEEDS_REFINEMENT，运行器拒绝执行而非创建空脚本。
- 迁移旧文档时先列出所有 ID，逐项核对迁移前后 ID 集合和数量，保留原断言及既有未提交修改；未知来源和缺失断言标记 `NEEDS_REFINEMENT`，不得推断为可执行。新增、修改、退休、迁移后均检查唯一 ID、索引链接、需求覆盖、Fixture 关联和报告引用。

### 通用门禁与项目实现边界

- 本 skill 只规定执行前后必须可核验的条件，不规定账号池文件格式、手机号范围、登录实现、数据库驱动、脚本语言或项目目录布局。账号注册/租用、获取会话、构造业务 Fixture、Case 固定脚本及批次运行器由项目 `.issuekit/testing/` 实现；不得把某个项目的账号、密钥、接口或 SQL 写进通用 skill。
- 批次执行前，项目实现必须输出可核验清单：明确环境及实际被测版本、服务和数据库身份、Case ID@revision、每条 Case 的账号/租约与前置状态、凭据来源、写入范围、复位或保留策略。校验会话归属与 UID/环境一致，校验服务实际数据源而非仅比较上下文文件中的声明；同一可变主体不能并行复用。
- 对每条 Case 做前置门禁：缺账号或过期凭据、服务未启动、数据源不明、Fixture 不符、缺写入授权或固定脚本时，标记具体的 `BLOCKED`/`NOT_RUN` 原因，禁止发起有副作用的业务动作；不得临时用其他账号、连接或手工生成步骤绕过。一次性前置状态用新主体或已审查的重置方案，不能在旧账号上假装首次运行。
- 固定脚本必须真正向声明的服务发起请求，并在需要时回读数据库、日志或异步事实；单测、Mock 服务和脚本语法校验只证明脚本质量，不计入真实业务验收。运行报告分别记录“脚本检查”和“真实环境执行”。批次可以显式选取部分 Case，但须报告选取范围、遗漏的 ACTIVE Case 和 `INCOMPLETE_EXECUTION`，不得称作全量验收。
