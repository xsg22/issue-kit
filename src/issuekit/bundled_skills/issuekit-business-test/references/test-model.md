# 测试模型与覆盖方法

## 业务模型

从需求和代码中提取五类对象：

1. 参与者：用户、管理员、系统任务、外部平台；
2. 实体：订单、任务、资源、额度、库存、权限；
3. 状态：实体状态及允许的状态转换；
4. 规则：输入、条件、计算和结果；
5. 副作用：数据库、消息、日志、文件、通知和外部调用。

## 覆盖维度

每个 Case 至少标注一个覆盖标签，核心 Case 通常需要组合：

```text
happy_path
boundary
negative
state_transition
idempotency
data_integrity
```

高风险业务增加：

```text
concurrency
retry
dependency_failure
security
rollback
```

## 状态机检查

对每个关键实体列出：

```text
当前状态 -> 触发动作 -> 中间状态 -> 成功状态
当前状态 -> 触发动作 -> 失败状态
当前状态 -> 非法动作 -> 拒绝结果
```

不能只测状态查询，要验证状态转换的入口、持久化、异步收口和重复事件行为。

## 状态变化契约

每个 Case 必须把状态变化拆成两条并行轨迹：

| 轨迹 | 必须回答的问题 |
|---|---|
| 用户可见状态 | 用户操作前看到什么；操作后看到什么；哪些按钮、页面、提示或后续动作发生变化 |
| 系统状态 | 数据库实体、资源账本、窗口、订单/任务、消息和外部资源从什么值变成什么值 |

标准写法：

```text
业务状态：BEFORE -> ACTION -> INTERMEDIATE -> AFTER
系统状态：before 字段快照 -> prepared 字段快照 -> after_response -> after_async
变化量：field_a +N，field_b -N，field_c 不变
禁止变化：field_d 不得创建/修改；不得出现负数、重复流水或跨窗口结转
```

### 状态变体分析

生成用例前先建立变体矩阵，至少比较：主体状态、权限等级、资源来源、资源窗口、输入边界和异步结果。只有当需求规定的用户结果、允许动作、状态转换和数据 delta 完全相同，才可以合并变体。

合并时必须记录：

- 已比较的变体；
- 比较的字段和规则；
- 代表变体及选择理由；
- 未单独执行的变体和覆盖依据。

任何状态差异都要拆 Case。例如同一操作在两种资源状态下，如果一个成功扣减、另一个返回业务错误，就不能合并成一个笼统的资源消费 Case。

## 测试预言机层级

优先使用以下顺序建立断言：

1. 需求规定的用户可见结果；
2. 稳定接口契约；
3. 数据库状态和不变量；
4. 异步任务和外部资源；
5. 日志作为定位证据，而不是唯一业务成功证据。

日志中出现“成功”不能替代数据库和接口结果；数据库状态正确也不能替代用户实际拿到的响应。

每条状态/资源 Case 还必须明确：

- 操作前用户可见状态和操作后用户可见状态；
- 操作前系统字段和操作后系统字段；
- 每个可变字段的精确 delta、单位、舍入和窗口归属；
- 允许变化的字段与明确禁止变化的字段；
- 中间状态、异步收口状态及超时处理。
