# 自动化执行循环

## 一轮验收

1. 读取有效需求意图及其来源，复用存在的技术方案、代码和相关项目测试知识；缺文件不阻断，未确认关键规则只阻断关联 Case；
2. 生成需求覆盖矩阵和详细 Case；
3. 检查当前机器的接口、数据库、日志、异步和认证能力；
4. 生成执行准备报告，列出全部 Case 的可执行、部分可执行和阻塞状态；
5. 为额度/余额/库存/次数等可变资源 Case 构造固定 Fixture，记录复用和复位策略；
6. 生成依赖图，标出串行 Case 和可并行 Case；
7. 按 Case 准备数据，保存 `before`/`prepared` 快照；
8. 执行真实用户动作或接口模拟，保存请求和响应；
9. 等待同步或异步收口，保存 `after_response`/`after_async` 快照；
10. 查询日志、消息、任务、业务实体、可变资源和最终资源；
11. 按断言判定结果，并保存所有证据索引；
12. 对照清单确认没有遗漏 Case。

## 失败后的循环

失败时先区分：业务实现错误、测试数据准备错误、环境或版本错误、外部依赖失败、证据查询能力不足。

只有确认属于实现问题时才进入修复计划。修复后重新执行受影响 Case 和相关回归 Case，不覆盖原始执行记录。

## Fixture 规则

同一个 Fixture 可以服务多个 Case，但只允许复用“定义”，不允许无条件复用已经被消费后的运行态数据。对可变资源、余额、库存和次数，必须在每个 Case 前恢复到指定值，或者为每个 Case 分配独立主体。

Fixture 必须记录：`fixture_id`、初始化目标、初始化前后快照、复用的 Case、每次复位记录、是否允许并行、清理或保留策略。

## 全量执行规则

主执行器维护完整 Case 状态表。无论使用多少子 Agent，最终报告都必须逐条列出全部 Case。未执行、执行中断、子 Agent 未返回或证据未收齐的 Case，不能被静默过滤。

## 结果要求

已证实任一必需断言失败时判 `FAIL`，不能被证据缺失降级。未证实失败且关键证据缺失时判 `PARTIAL_PASS`；全部关键断言有证据通过、仅辅助证据缺失时判 `PASS_WITH_WARNINGS`；所需证据完整且全部必需断言通过才判 `PASS`。数据库或日志的重要性依据 Case 预期确定，不能因查询能力缺失而降低其重要性；查询不到也不能直接归因于业务失败。
