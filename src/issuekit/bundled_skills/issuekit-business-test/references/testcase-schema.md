# 真实业务测试用例结构

每条用例是执行协议，必须单独包含以下内容，不能靠阅读相邻用例补齐：

1. 业务目标和需求来源；
2. 用户、业务实体、权限和数据前置状态；
3. 具体输入值和边界值；
4. 真实用户操作及接口映射；
5. 接口响应断言；
6. 数据库四阶段断言；
7. 异步任务、日志、消息、文件或交付物断言；
8. 单一且无歧义的通过标准；

以上属于规范定义。真实结果、证据索引、预期/实际差异、结论和 FAIL 原因只写入每轮独立运行报告，按 `case_id + revision + commit + fixture_id` 关联，不放入 Case 定义。

推荐使用以下顺序，保证用例可以直接交给执行器：

```markdown
# CASE-001：{明确业务场景}

## 1. 业务目标
## 2. 需求事实与实现事实
## 3. 前置状态
## 4. 测试数据准备
## 5. 用户操作步骤
## 6. 接口断言
## 7. 数据库断言
## 8. 日志、消息和异步断言
## 9. 通过标准
## 10. 失败判据与所需证据清单
```

## 需求是预期结果的唯一优先依据

用例顶部引用当前有效需求意图及对应验收标准/原文，记录来源（任务、已确认讨论或文档）和生效版本或确认时间。缺少需求文件不阻断；关键规则冲突或缺失只阻断关联 Case。技术方案、接口文档、代码和数据库仅用于补充执行方式、接口字段和观测手段。代码行为与明确需求冲突时，仍按需求写预期，结论应判 `FAIL`/`IMPLEMENTATION_GAP`；不能把代码现状改成通过标准。只有需求本身互相矛盾或未定义时，才标为 `REQUIREMENT_CONFLICT` 或 `ASSUMPTION`。

## 前置状态必须可查询

前置状态不能只写业务形容词，必须映射到可查询字段和值：

```text
主体：id=...
角色：operator
业务状态：state=ACTIVE
可变资源：resource_a.available=1
任务：不存在同一幂等键的历史任务
```

如果某个状态无法从当前数据库、接口或日志查询，标记为 `UNKNOWN`，并在执行准备报告中说明。

## 状态变化必须双轨记录

每个 Case 定义必须同时规定以下两条预期轨迹，运行报告另记实际轨迹，不能只写最终接口响应：

1. **用户可见状态**：用户在操作前、处理中和最终收口后看到的状态、提示、剩余值、可执行动作和不可执行动作。
2. **系统状态**：数据库实体、资源窗口、账本流水、订单/任务、消息和外部资源的字段和值变化。

每个可变字段都要写精确的 `before -> prepared -> after_response -> after_async` 和 delta。字段没有变化也要明确写 `unchanged`。同时列出禁止变化，例如不得出现负数、重复扣减、跨窗口结转、跨类型扣减或无输入的任务/交付物。

多种用户状态、权限等级或资源来源只有在需求规定的用户结果、状态转换和数据 delta 完全相同的情况下才能合并。合并 Case 必须增加“变体选择”段，列出已比较的变体、比较字段、代表变体理由和未执行变体的覆盖依据；存在任一差异时拆分 Case。

## 每个动作都要有中间状态

多步骤业务必须记录：

```text
执行前 -> 请求提交后 -> 预占/处理中 -> 外部任务接受后 -> 成功/失败收口后
```

例如额度业务不能只验证最终余额，还要检查预占、确认消费、释放和补偿账本。

## 状态写法

不要写“额度较少”，要写：

```text
entity_state=ACTIVE
resource_a.available=1
resource_b.available=2
resource_c.available=5000
```

## 数值边界

对于每个有计算规则的输入至少覆盖：小于边界、等于边界、大于边界、余额为 0、余额刚好够、余额差 1、重复操作和失败重试。

用例应明确写出计算结果。例如某个业务规则的阈值为 100 时，应明确验证 99、100、101，以及资源余额为 0、刚好够和差 1 的情况。具体阈值必须来自有效需求或已确认契约；实现只能补充观测事实，不能替代业务预期，不得由通用 Skill 臆造。

## 精确断言

每一步都要有与输入对应的预期。不得写“返回不足或失败”“按业务处理”“不超扣”等未说明最终行为的短句。至少写清：

- HTTP 状态和外层业务 code；
- 响应里的具体业务码及需求规定的状态字段；
- 关键字段具体值、单位和边界；
- 数据库哪些行/字段不变或变化多少；
- 任务/订单/交易最终状态；
- 是否创建下游任务、交付物或外部调用。

如现有实现给出的错误码与需求期望冲突，应分别记录 `REQUIREMENT_EXPECTATION` 和 `CODE_FACT`，以需求判通过，不得模糊成两个均可接受结果。

## 实际结果与失败原因

每条 Case 执行后在本轮独立运行报告填写自己的真实结果，不能回写定义，最少包括：时间、UID、环境和代码版本、请求/响应、数据库前后快照、任务/账本 ID、证据路径、预期与实际差异、结论。未执行为 `NOT_RUN`，不能空白。

`FAIL` 必须写直接失败原因，不得只写“未通过”。涉及状态流转、账务/资源变化、重复或异步问题时继续记录 5 Why、根因和下一步修复/回归计划。

结果记录建议格式：

```text
Expected: 需求规定的精确状态码、字段值和数据变化
Actual: 实际 HTTP/业务响应、实际 DB diff、实际异步终态
Difference: 无 / 字段级差异
Evidence: request/response、snapshot、traceId、业务 ID 的路径
Verdict: PASS / PASS_WITH_WARNINGS / PARTIAL_PASS / FAIL / BLOCKED / NOT_RUN
Failure reason: FAIL 必填；NOT_RUN/BLOCKED 写未执行原因
```

## 结论等级

按以下含义判定，不能以证据缺失掩盖已证实的失败：

- `FAIL`：已有足够证据证明任一必需断言失败，优先于部分通过或警告，即使其他证据尚不完整。
- `PARTIAL_PASS`：核心动作已执行、未证实失败，但关键断言证据缺失。
- `PASS_WITH_WARNINGS`：全部关键断言有证据通过，仅缺非关键辅助证据。
- `PASS`：所需证据完整，全部必需断言通过。
- `BLOCKED` / `NOT_RUN`：核心动作无法执行或未执行，必须写明原因，不能算通过。

数据库或日志是否为关键证据取决于该 Case 的有效预期，不由工具是否可用决定。

## 最低结构校验脚本

使用本 Skill 的 `scripts/validate_testcase_document.py <path> --kind definition|report`；默认 `definition`。它只检查最低结构与明显模糊描述，不判断断言是否正确、证据是否真实或功能是否通过。

脚本接受字段行“字段：非空内容”（支持粗体/列表标签），也接受 Markdown 字段标题下的非空正文。每个 Case 必须有实际 Markdown 标题，例如 `# CASE-001：名称`；代码围栏中的模板标题不算 Case。字段不能跨 Case 借用。

- 公共头部位于第一个 Case 之前，包含 `环境`（定义可用 `环境绑定` 描述执行时绑定）和 `数据隔离`，不适用也要说明原因。
- 定义的每个 Case 包含 `需求来源`、`前置状态`、`数据准备`、`操作步骤`、`预期结果`、`数据库断言` 和 `通过标准`；数据库不适用时明确说明。预期应给出具体值和不变量，不填写运行实际结果。
- 报告头部另包含 `test_run_id` 和 `被测版本`。每个 Case 包含 `Case 引用`（同 ID 的 `CASE-001@r2` 等固定修订引用）、`实际结果`、`证据` 和 `结论`；无需重复定义中的完整步骤和预期。失败/阻塞/未执行补 `失败原因` 或 `未执行原因`，部分通过/警告补 `限制`。未执行时实际与证据字段明确写未执行/无证据及原因，不伪造运行。

旧的定义/实际混合大文档应先保留历史记录，再拆出规范定义与独立运行报告；不要为了通过新校验把历史真实结果删除或填入虚假内容，也不要把脚本通过当作完成迁移或验收。
