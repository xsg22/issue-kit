## 执行循环

真实验收不是一次性运行：

1. 生成并评审 Case；
2. 探测当前机器能力并生成 Readiness 报告；
3. 构造测试批次 Fixture，并为每个 Case 分配独立或可复用的 Fixture；
4. 生成执行计划，标明串行依赖和可并行 Case；
5. 准备测试数据并保存快照；
6. 执行本轮清单；部分失败不影响独立 Case 继续，授权、隔离或前置状态失效时停止受影响动作并记录未执行原因；
7. 记录接口、数据库、日志和异步证据；
8. 对失败项做 5 Why，区分代码、数据、配置、环境和证据缺失；
9. 汇总根因与修复建议；仅在本次明确授权范围内修复代码或配置，未授权的修复交由开发者处理；
10. 重新执行受影响和失败的全部 Case，并补跑关联回归；
11. 输出本轮和累计结果。

每一轮必须使用新的 `test_run_id`，不能覆盖上一轮证据。

修复回归时必须记录失败 Case、根因、修复 commit、重新执行的 Case、未重跑的关联 Case 及原因。不能只重新执行成功路径来替代对原失败边界的验证。

每个 Case 的执行结果都必须单独记录：`expected`、`actual`、差异、证据、结论和失败原因。`FAIL` 必须写出可复现的直接原因；复杂失败再追加至少 5 Why、根因、修复建议和回归 Case。`NOT_RUN`/`BLOCKED` 必须说明阻塞条件，不能留空或记成 PASS。

### 并行执行规则

可以使用子 Agent 并行执行相互独立的 Case，但主执行器必须先完成全量 Case 清单、Fixture 分配和依赖图。只有以下条件全部满足才允许并行：

- 测试账号/租户不同，或有可靠的状态隔离；
- 不共享可变资源、库存、业务订单、任务、文件、缓存键和幂等键；
- 不依赖同一个外部限流配额或顺序状态；
- 数据库、日志和业务 ID 能按 `test_run_id`/`case_id` 唯一归属；
- 一个 Case 失败不会改变另一个 Case 的预期前置状态。

无法证明独立时必须串行执行。子 Agent 只能负责已分配的 Case，不能修改其他 Case 的数据或结论；主执行器负责汇总、补跑失败项并确认清单完整。

### 全量完成门禁

执行报告必须包含测试清单中的每个 Case。存在未执行 Case 时，整轮结果不能标记为完成，只能标记 `INCOMPLETE_EXECUTION`，并说明未执行原因和下一步。
