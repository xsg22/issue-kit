# IssueKit 代码合并

## 定位

充分发挥 Agent 的分析和实现能力，自主选择适合当前任务的合并方式、工具和验证手段。本 skill 只规定合并原则与兜底门禁，不规定 Git 命令、操作顺序或固定合并策略。门禁用于防止错误结果被交付，不替代背景调查和业务判断。

## 合并原则

### 相信改动有背景，理解目的后再合并

- 默认每项改动都有可以追溯的背景，主动寻找并交叉核对双方的需求、设计、提交历史、PR 讨论、测试与实际调用链，直到能够解释为什么修改、要保留什么行为以及受哪些约束。
- 使用已有 IssueKit 上下文：`.issuekit/config.yaml` 中的 `issues_dir`（默认 `issues`）、相关 Issue 文档，以及 `.issuekit/knowledge/` 中的约定和模块知识。没有 Issue、缺少文档或某个来源不可访问，都不等于背景不存在；继续从其他证据还原，不把查背景直接交给用户。
- 背景材料可能过时，代码也可能偏离需求；以相互印证的证据建立判断，明确区分已确认目的和推断，不凭分支名、提交新旧或局部 diff 猜测业务取舍。
- 以共同基线理解双方各自引入了什么变化，区分原有行为、独立修复和演进中的契约；避免把版本差异误当成可以丢弃的旧代码。

### 保留业务意图，适配真实契约

- 理解双方目的后，保全本次应保留的有效能力；意图可以兼容时主动完成适配，确实互斥时说明取舍及其依据，不机械选择整边代码。
- 合并范围包含受影响的调用方、测试、配置、数据契约和必要文档；没有文本冲突不代表行为兼容，消除冲突标记也不代表合并完成。
- 修复合并引入的问题，不借机加入无关功能、重构或凭空创造新的业务规则。
- 保留意图不等于保留所有代码：有意删除、撤销、替换或已被覆盖的实现，应依据当前目标正确舍弃；若缺陷修复仍有价值，将其迁移到有效实现，不复活废弃链路。双方独立新增同名能力时，也应收口到一致职责，避免重复执行或重复副作用。
- 识别选定变更对其他提交、数据库迁移、配置和上下游契约的依赖；缺失依赖必须解决或明确阻塞，不能只搬运局部代码，也不能以补齐依赖为由擅自扩大授权范围。
- 一方演进接口、另一方修复缺陷时，应将修复适配到目标契约，既保留修复效果，也不恢复已被有意替换的旧设计；不能只因代码来自稳定分支或较新提交就赋予整边优先权。
- 按产物语义判断合并结果：源码关注行为，依赖声明与锁文件关注一致性和实际依赖变化，生成文件关注权威输入与可再生成性，版本及发布元数据关注目标发布线。项目专用的优先规则不能推广为通用规则。
- 代码共用不代表环境和业务策略相同：保留有依据的区域、部署和版本差异，不将一方的默认值、服务地址或开关行为意外传播到另一方。凭据、账号会话及其他运行态数据不按源码拼接，不混用不同环境或账号的状态，也不在调查输出中泄漏敏感值。

### 以功能保全衡量合并结果

- 合并结果应保留目标分支已经具备的有效能力，并纳入本次选定的源分支能力；只有有依据的废弃、替代或明确授权的取舍可以改变这一边界。目标分支此前从其他分支合入的成果同样受保护，不能只关注这次新合入的功能。
- 在受影响范围内建立可解释的能力对照：合并前各方能做什么，合并后由哪里承接、如何触达、适用条件和结果是否保持。对照可以简明表达，不要求固定表格或新增文档，但每项有效能力都应有去向。
- 保全的是行为而不只是代码存在：实现仍在但入口不可达、注册或路由丢失、配置关闭、数据传递中断或必要副作用消失，都属于潜在功能丢失；替换实现应证明原有有效能力有等价承接。
- 审视合并结果相对各方基线的语义变化，重点解释消失、缩减、覆盖和默认行为改变。检查范围不能止于冲突块，还应涵盖自动合并及解决冲突时连带改写的上下文；不能仅以“相对目标分支新增了什么”判断完整性。
- 多分支集成以最终组合为准：后续合入不得覆盖前面已保留的有效能力；历史上曾合入、提交仍在祖先链中、某一轮验证通过，都不能单独证明功能在最终结果中仍然存在。
- 双方仍有效的回归约束都应保留，必要时适配到新的实现和测试边界。测试或断言被删减时，须能解释对应能力为何废弃或由何处继续验证；只验证新功能或把测试同步改成缩水后的行为，不能证明功能保全。

### 让证据聚焦，让验证覆盖组合结果

- 根据冲突摘要、局部差异和相关索引信息聚焦调查；上下文不足时主动扩展到完整实现和调用链，不把节省上下文当成省略业务理解的理由。
- 冲突不只表现为文本标记，还包括新增、删除、重命名、二进制或目录层面的分歧；未发现标记或普通文件冲突，不能单独证明合并干净。
- 双方各自验证通过，不代表组合后的实现通过。区分文本冲突、编译或契约不兼容、业务回归和环境故障，依据真实失败证据修复，不能靠反复重跑掩盖问题。
- 对原有失败的归因须有基线对照或等价证据；保留并报告原有缺陷，不借合并无限扩展修复范围。不得将新增回归归为历史问题，也不得把存在已知失败的结果称为全绿。
- 验证业务不变量而不只验证编译：关键字段、调用顺序、幂等条件、状态流转和外部副作用在组合后仍须符合目的；测试应保留双方仍有效的场景，断言变化须有业务依据，不能仅追随合并后的实际输出。
- 验证范围与风险相称，优先复用项目已有质量门禁；已有证据仅在对应版本和覆盖范围仍适用时复用，不机械重复全量检查，也不把针对性测试夸大为完整验收。
- 过去的冲突解决记录可以作为候选方案复用，但必须重新核对当前背景、契约和结果；相同冲突形状不等于相同业务答案。

### 尽力完成，人工兜底

- 对可通过调查、实现和验证解决的问题主动推进；一种方式失败时根据证据调整，不因首次冲突、构建失败或材料缺失就转交人工。
- 业务目标互斥时，已有明确需求、目标契约或用户指定优先级足以裁决的，由 Agent 自主取舍并解释依据；只有合理可用的调查和验证仍不足以裁决，或继续推进超出授权、存在无法控制的数据损失风险时，才保留现场和已完成成果，请人工介入。
- 人工介入时提供具体决策点、已查背景与证据、尝试及结果、可选方案和各自影响，并给出建议；避免只说“有冲突，请手工解决”。独立且安全的部分可以继续，依赖该决策的部分不得擅自定夺。

## 兜底门禁

以下条件不满足时，不得把结果宣称为已完成或可安全合入；优先补齐，确实无法补齐时说明阻塞并交由人工决定。

- **目标明确**：仓库、源与目标分支或 PR、实际提交基线、区域及本次合并目的可核对；不把开发基线、集成分支与发布分支混为一谈。
- **意图可解释**：影响业务行为的取舍有背景依据；未解决的关键歧义不能以猜测掩盖。
- **功能无无故丢失**：受影响范围内，目标分支原有能力、此前集成成果与本次选定源分支能力均有明确去向；删除、覆盖、行为缩减或不可达变化须有依据。没有等价承接或明确取舍证据时，视为待解决的回归，不得以冲突消失、编译通过或新功能测试通过放行。
- **工作成果受保护**：其他任务的未提交改动、已有合并状态和工作区得到保护，不通过覆盖、强制清理或夹带提交换取表面成功。
- **结果经过验证**：不存在未解决的合并冲突；验证覆盖实际合并结果及受影响契约，关键业务风险有相应检查。失败须查明是否由本次合并引入；未执行、被阻断或无检查配置不能记为通过，也不能通过删除有效校验或降低断言掩盖失败。
- **证据与版本一致**：验证证据对应明确的代码版本；双方基线或结果变化后，重新判断原有证据是否仍适用，并补充必要验证。
- **合入时仍有效**：最终合入的源版本与已验证版本一致，目标基线仍满足验证前提；不能只检查一次后任由远端更新。无法保证时不得沿用旧的通过结论。
- **动作符合授权**：遵守用户与项目的提交、推送、PR 合入、发布及线上写入权限；调用本 skill 不自动扩大授权。任何动作不得因工具默认行为绕过授权。
- **交付状态真实**：清楚区分本地修改、已提交、已推送、PR 已合入及已发布；依赖远端结果的结论须以实际回读为准，清理不得损失仍需保留的成果。
- **清理有归属依据**：明确分支和工作区的实际归属、后续用途及未保存内容；不凭目录名、创建时间、已创建 PR 或看似空闲就认定可删除。失败或仍待人工裁决时保留恢复与继续工作的条件。

## 交付

简明说明实际仓库与分支、源和目标版本、各方有效能力的保全证据、有依据的废弃或替代、验证范围、实际完成的动作，以及剩余风险或需要人工裁决的问题。相关 Issue 已存在且有重要合并决策时，将结论补充到适合的已有文档，不强制创建新的报告或模板。
