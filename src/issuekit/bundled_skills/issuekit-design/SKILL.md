# 技术方案

帮助开发者决定“如何以合理成本完成目标，并保全现有能力”。交付足以指导实现与评审的技术决策，深度与变更风险相称。

## 输入与事实

已明确的用户目标、任务说明、需求文档、讨论和既有设计均可承载需求，不以 `requirement.md` 或 Issue 目录存在作为前提。

复用项目约定与相关知识，核对受影响的入口、调用方、数据、配置和外部依赖，辨明资料是否仍然有效。已有 Issue 可从用户提供的信息或分支定位，不能仅凭分支名称断言需求。

需求尚有关键歧义时，先追溯背景与已有决策。可独立设计的部分继续；影响方案正确性的业务取舍缺少依据时，提出具体决策点并标明依赖，不擅自补成确定需求。

## 设计原则

- 优先复用已有边界、组件和平台能力。比较实际可行的方案，说明关键取舍；不为小变更创造新框架、接口或配置。
- 设计围绕目标与约束，而非固定分层或文件清单。识别真正的技术未知项，按需查证文档、源码或原型；区分已验证事实、估算与待验证假设。
- 保全有效业务意图，明确既有能力由哪里承接；有意替代、删除和兼容缩减须有依据。完整追踪调用方、下游和异步副作用，不只设计新增入口。
- 变化的契约应具体到实现与验收所需：接口输入输出与错误语义、数据约束与索引、状态流转、配置默认值、权限及异常恢复。示例不能替代契约；敏感信息不进入文档。
- 按实际风险评估版本兼容、性能与容量、并发幂等、数据迁移、可观测性和故障恢复。涉及迁移时明确依赖、执行顺序及回退限制，避免把不可逆动作写成可无损回滚。
- 区分本次必需改动与外部前置依赖，不把发现的相关问题自动纳入实施范围。

## 交付结果

输出所选方案、关键依据与替代方案、受影响边界和契约、兼容或迁移考虑、风险及验证方式。复杂变更可补充架构与时序图、接口示例、数据变更说明和实施依赖；简单变更无需填满所有章节。

需要落盘时，复用 `.issuekit/config.yaml` 的 `issues_dir`（默认 `issues`）、已有 Issue 目录与 `.issuekit/templates/technical-design.md`（如有），通常写为 `technical-design.md`。提供可定位的代码依据，避免编造不存在的组件、路径或接口。

可以给出本项目必要的实施顺序，但不把所有任务限制为同一套开发步骤。验证考虑说明什么结果能证明设计成立，不能表述为测试已经通过。

## 完成门禁与边界

- 方案覆盖明确目标、相关调用链及有效能力，关键技术选择有依据，依赖与风险能够被实施者识别。
- 契约、数据和配置之间无已知矛盾；重要未知与人工决策点明确，未解决的问题不包装成最终定案。
- 设计与已确认意图不一致时说明差异，不能静默改写需求。已知方案缺陷应在影响依赖实现前处理。
- 本 Skill 交付方案，不隐含代码实现、数据库执行、基础设施修改或发布授权。报告实际产物与待决事项，后续节点可独立选择。
