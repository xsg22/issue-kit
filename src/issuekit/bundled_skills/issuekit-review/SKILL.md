---

## 用户输入

用户可以指定 issue ID，也可以从当前 git 分支自动推断。

## 概述

本 skill 通过交叉验证代码变更与需求、技术方案、测试方案、架构边界、实现细节、编码规范和交付文档，进行全面的代码审核，生成便于人工复核和修复的审核文档。业务功能完整只是审核的一部分，不能替代设计、实现和运维质量审核。

## 前置条件

- Pull Request 已创建
- `release-note.md` 存在（或至少代码变更已在分支上）

## 工作流程

### 第 0 步：先读取知识约定并规划任务

在开始代码审核规划前，优先执行：

1. 阅读 `.issuekit/knowledge/conventions.md`（如有）
2. 阅读 `.issuekit/knowledge/` 下与当前审核范围相关的已有知识摘要（如有），若存在 `.issuekit/knowledge/modules/` 对应模块文件则优先阅读
3. 基于上述约定与已有知识，再开始后续审核步骤

### 第 1 步：定位 Issue 并收集材料

1. 读取 `.issuekit/config.yaml` 中的 `issues_dir` 配置项，获取 Issue 文档存放目录（默认为 `issues`）
2. 定位 issue 目录（从用户输入或当前分支，issue 目录位于 `{issues_dir}/{issue-id}/`）
3. 阅读所有 issue 文档：`requirement.md`、`technical-design.md`、`test-plan.md`、`release-note.md`
4. 获取代码差异：`git diff master...HEAD`
5. 获取 PR 信息（如有）：`gh pr view`

### 第 2 步：多维度审核

#### 2.1 业务功能完整度
- 逐条对照用户故事和验收标准检查代码变更
- 验证每个 User Story 的流程是否已实现
- 标记未实现或部分实现的需求
- 检查正常流程、失败流程、重复请求、重试、乱序、并发、空数据、越权和历史数据场景
- 检查接口返回、状态码、错误码、客户端兼容字段是否覆盖需求约定

#### 2.2 方案一致性
- 对照技术方案验证实际实现
- 检查接口设计是否与实现一致
- 检查数据库变更是否与设计一致
- 标记偏离

#### 2.3 架构与代码设计
- 检查模块边界、依赖方向和职责归属是否符合项目架构；禁止把业务规则放进 Controller、Mapper 或无领域含义的公共工具类。
- 检查一个类、方法或模块是否只承担一个主要职责；发现查询、状态机、事务、第三方调用、消息投递和响应组装堆叠时，要求拆分。
- 检查新增抽象是否真正减少复杂度；识别万能 Service、纯转发层、重复 Adapter、过度封装和为了兼容而扩散历史别名。
- 检查状态机、领域事实边界、事务边界、幂等键、重试边界和异步 Outbox/消息投递是否有清晰的所有权。
- 检查外部来源或供应商特有逻辑是否封装在 Adapter/Processor，公共流程是否只处理稳定领域模型。
- 检查新增接口、DTO、BO、DO、枚举和配置是否放在正确模块，是否泄漏实现细节或破坏公共契约。

#### 2.4 代码实现正确性
- 沿调用链核对入口校验、参数转换、核心分支、持久化、事务提交、异步投递和响应组装，确认实现顺序正确。
- 检查每个返回分支是否完成必要的状态落库、事件记录、资源释放和日志记录；不能只检查主成功分支。
- 检查异常分类是否正确：参数/业务拒绝、临时依赖失败、并发冲突和系统故障不能混成同一种结果。
- 检查重试是否安全：重复执行不会重复扣费、重复发放、重复冲正或覆盖更新的事实；重试是否保留原始上下文。
- 检查事务边界和锁的范围，避免外部 HTTP/SDK 调用持有数据库锁；检查并发下的唯一键和幂等查询是否可靠。
- 检查第三方事实是否经过验签、环境、账号、商品、金额、币种和时间校验；禁止根据客户端自报状态或通知到达顺序作关键决策。

#### 2.5 测试覆盖度
- 验证测试方案是否覆盖所有需求点
- 检查关键代码路径是否有对应测试用例
- 识别未覆盖区域

#### 2.6 可维护性与人工 Review 友好度
- 命名规范（类名/方法名/变量名）
- 异常处理（不吞异常、有意义的错误信息）
- 日志记录（关键路径有日志、级别合理）
- 边界条件（空值检查、数组越界、并发安全）
- 代码重复（可提取的公共方法）
- 分层职责（Controller、Service、Domain、DAO、Adapter、Assembler 边界清晰）
- 复杂度（圈复杂度、嵌套层级和单类职责是否需要拆分）
- 检查新增或修改的公共接口、类型、方法和字段是否按项目约定提供必要的文档或注释，说明职责、语义、关键入参、返回值和副作用；语言与格式遵循项目规范。
- 方法注释必须回答“做什么、为什么这样做、成功/失败后产生什么状态或副作用”；禁止只翻译方法名或描述变量赋值。
- 复杂 `if/else`、`switch`、异常分支、状态流转、异步回调、重试和兼容分支，应在代码意图不能清楚表达时补充注释，说明该分支的业务目的、进入条件和不能合并的原因；注释使用领域中立的描述，不绑定具体业务名称。
- 一个方法同时处理多个业务阶段时，检查是否应拆成命名清晰的步骤或策略；不能把来源特殊逻辑、状态机、数据库查询、第三方调用和响应组装堆在一个公共方法中。
- 魔法值必须按语义收口：有限且需要分支穷举的业务状态、类型和模式优先使用枚举；稳定的协议字符串、错误码、来源标识、事件 ID 前缀和固定业务文案使用当前语言及项目约定的常量机制。
- 禁止在条件判断、`switch`、异常构造、日志拼接和持久化组装中散落同一字符串或数字；常量/枚举名称必须能表达业务语义，不能只用 `VALUE_1`、`TYPE_A` 等无意义别名。
- 注释必须与当前代码行为一致；发现注释描述旧流程、旧接口或旧状态时，列为审核问题。
- Review 报告必须按关键流程列出“入口 -> 验证 -> 状态判断 -> 持久化 -> 异步/外部调用 -> 返回结果”的执行路径，帮助读者快速建立上下文。

#### 2.7 可观测性与运维性
- 关键业务路径必须记录可关联的业务标识、事件 ID、资源标识、对象 ID 或任务 ID；不得记录敏感凭据。
- 日志级别要与处理结果一致：正常幂等、可重试故障、永久拒绝和系统异常不能全部使用同一级别。
- 检查失败码、状态码、重试次数、租约、Outbox 和人工补偿信息是否足以支持排查，不要求依赖完整原始 payload 才能定位问题。
- 检查定时任务、消息消费、回调重放和外部依赖失败是否有明确的重试上限、退避、告警和死信/人工处理路径。

#### 2.8 安全审查
- SQL 参数化（无字符串拼接 SQL）
- XSS 防护（输出转义）
- 敏感数据（密码/token 不明文、不日志）
- 权限校验（接口鉴权完整）
- 日志使用参数化占位符，禁止字符串拼接；认证、外部回调和第三方集成日志不得输出 token、签名载荷、Authorization、密钥或包含凭据的 URL。

#### 2.9 性能审查
- 无 N+1 查询问题
- 大批量操作有分批处理
- 热点数据有缓存策略
- 数据库索引覆盖查询条件

#### 2.10 兼容性审查
- API 向后兼容
- 数据库迁移安全
- 客户端版本兼容

#### 2.11 验证门禁审查
- 检查项目是否存在并实际执行与其技术栈适配的编译或类型检查、单元测试、集成测试、静态分析及必要的文档检查等质量门禁；没有自动门禁时必须在报告中明确标记为缺口。
- 检查新增或修改的代码是否有对应测试；复杂分支必须覆盖正常、失败、重复、重试、并发或乱序场景。
- 检查新增数据库索引、字段或迁移是否有版本化 SQL、执行前检查、执行后校验和回滚说明。
- 验证失败不能仅以“已有历史问题”带过：必须说明失败命令、失败位置、是否与本次改动相关以及剩余风险。

#### 2.12 文档与交付一致性
- 检查接口、状态、错误码、数据字段、回调流程、部署配置和迁移步骤是否同步更新文档。
- 检查文档描述是否与代码当前行为一致，尤其是旧链路/新链路、灰度开关、客户端兼容和回调重试语义。
- 检查 release note、部署说明、回滚方式和数据库脚本是否足以让其他开发者完成发布和故障恢复。

### 第 3 步：生成审核文档

加载模板 `.issuekit/templates/code-review.md` 并填入审核结果。

审核文档必须按以下顺序组织：

1. **问题与风险**：先列发现的问题，再列总体结论；不要把问题埋在总结后面。
2. **严重级别**：使用 `P0`（阻断发布/数据安全）、`P1`（核心流程错误或高风险回归）、`P2`（应修复的设计/实现问题）、`P3`（可维护性或文档改进）。
3. **每个问题的证据**：提供绝对文件路径、行号、触发条件、实际行为和影响范围；不能只写笼统评价。
4. **修复建议**：说明建议调整的职责边界、状态流转、事务/幂等策略、测试补充或文档变更；避免只建议“重构一下”。
5. **未覆盖风险**：列出无法验证的环境、依赖、外部系统、数据库或质量门禁，并说明验证限制。
6. **通过项与摘要**：所有问题列完后，再汇总需求、设计、实现、测试和交付文档的通过情况。

人工 Review 的最低检查结果应包括：

- 关键入口和调用链是否易于阅读；
- 每个复杂分支是否能看出进入目的、状态变化和副作用；
- 公共流程与来源/供应商特殊逻辑是否分离；
- 失败、重试、幂等、并发和乱序场景是否有明确实现；
- 日志、常量、注释、测试和文档是否足以让未参与开发的人复核代码。

### 第 4 步：写入文件并报告

1. 将 `code-review.md` 写入 issue 目录
2. 报告审核结论：
   - **通过**：所有维度通过
   - **有条件通过**：有必须修复项，修复后通过
   - **不通过**：发现严重问题
